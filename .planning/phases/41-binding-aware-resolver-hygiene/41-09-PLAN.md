Wave 6 (gap closure): Close 41-REVIEW.md WR-05 by splitting the request-identifier vs dial-target identities in `ssh_connection_wrapper`'s error envelopes. Apply the reviewer's preferred option (a) — split the wrapper into two args — unless the call-site count makes it impractical.

Today (post Plan 41-03):
- `ssh_connection_wrapper` extracts `hostname = kwargs.get("hostname", args[0] if args else "unknown")` — that's the DIAL-TARGET identity, because Phase 41 callers (e.g., `discover_and_store`) call `ssh_discover_system(dial_target=row.connection_ip, ...)` and the wrapper sees `args[0]` (or `kwargs["hostname"]`) as that dial target.
- The wrapper writes `{"hostname": hostname, "connection_ip": hostname}` — both fields carry the dial-target value. The original requested identifier (`pve`) is lost.
- `discover_and_store`'s post-parse merge via `find_devices_by_hostname_or_ip` salvages the row identity for the discover path, but any caller of `ssh_discover_system` / `ssh_execute_command` that does NOT post-merge sees an envelope where `hostname=192.168.10.20` and the original `pve` is gone. `ssh_execute_command` is called directly by MCP tool dispatchers — no post-merge happens there.

Fix per 41-REVIEW.md WR-05 §"Fix" option (a):
1. Split `ssh_discover_system` (and any other `@ssh_connection_wrapper` callee) into two args: a `hostname` parameter that carries the REQUESTED identifier (the input the user passed, used for telemetry / row-routing identity) and a new `dial_target` keyword-only parameter that carries the actual TCP dial target. When `dial_target` is None or absent, it defaults to `hostname` (back-compat).
2. The wrapper's error envelope reads BOTH from kwargs:
   - `requested = kwargs.get("hostname", args[0] if args else "unknown")` — the requested identifier.
   - `dial_target = kwargs.get("dial_target", requested)` — the TCP dial target, defaulting to requested.
3. Every error envelope emits:
   - `"hostname": requested` (the requested identifier)
   - `"connection_ip": dial_target` (the dial target)
   When they're equal (legacy single-arg path), both fields carry the same value — identical to current behavior.
4. Audit `ssh_execute_command`'s envelope handler — apply the same split.

Call-site audit: per the WR-05 §"Fix" call-site analysis, `@ssh_connection_wrapper` decorates exactly two functions: `ssh_discover_system` (ssh_tools.py:528) and `ssh_execute_command` (ssh_tools.py:925). Both are reachable from MCP tool dispatchers and `sitemap.discover_and_store`. The blast radius is small enough that option (a) is practical.

Output: `error_handling.py::ssh_connection_wrapper` reads both kwargs; `ssh_tools.py::ssh_discover_system` and `ssh_tools.py::ssh_execute_command` accept `dial_target=` keyword-only param; `sitemap.discover_and_store` passes `dial_target=` when calling `ssh_discover_system`; one regression test exercising the bare envelope.

**parse_discovery_output coherence check (plan-checker WARN-03):** The success-path JSON `ssh_discover_system` returns is consumed by `sitemap.NetworkSiteMap.parse_discovery_output` (lines 76-152). The parser reads `connection_ip` via `data.get("connection_ip", "")` with NO normalization — it stores whatever the JSON carries. Therefore flipping the emitted `connection_ip` field from `hostname` (the post-Plan-41-03 dial-target literal) to `effective_dial = dial_target or hostname` is a faithful passthrough at the parser layer:
  - **Back-compat callers (no `dial_target` supplied):** `effective_dial == hostname`, so the JSON's `connection_ip` field is byte-identical to today.
  - **Phase 41 callers (e.g., `discover_and_store` passing `dial_target=row.connection_ip`):** the JSON's `connection_ip` field flips from the requested-identifier literal to the actual TCP target. `parse_discovery_output` writes that into the row's `connection_ip` column — which is exactly what Plan 41-03 wanted (the row's connection_ip column should reflect the actual dial target when discovery succeeds via a row-bound dial). The downstream `find_devices_by_hostname_or_ip` merge in `discover_and_store` continues to route on the requested identifier (the `hostname` field, which `parse_discovery_output` also writes from `data.get("hostname", "")`).

@pytest.mark.asyncio
async def test_envelope_split_request_identifier_from_dial_target() -> None:
    """Phase 41-09 WR-05: when ssh_connection_wrapper receives both
    ``hostname`` (requested identifier) and ``dial_target`` (TCP target)
    via kwargs, the error envelope emits them as distinct fields:
    ``hostname`` carries the requested identifier; ``connection_ip``
    carries the dial target.

    Pre-Phase-41-09 the envelope emitted both fields as the same value
    (the dial target) — the requested identifier was lost for any caller
    that did not post-merge through find_devices_by_hostname_or_ip
    (e.g., direct MCP tool callers like ssh_execute_command's tool
    dispatcher).

    See 41-REVIEW.md WR-05.
    """
    @ssh_connection_wrapper(timeout_seconds=10.0)
    async def stub_op(hostname: str, *, dial_target: str | None = None) -> str:
        raise TimeoutError("simulated SSH timeout")

    raw = await stub_op(hostname="pve", dial_target="192.168.10.20")
    envelope = json.loads(raw)

    assert envelope["status"] == "error"
    assert envelope["hostname"] == "pve", (
        f"Phase 41-09 WR-05: expected hostname='pve' (the REQUESTED "
        f"identifier), got {envelope.get('hostname')!r}. The original "
        f"identifier the user passed must survive on the envelope."
    )
    assert envelope["connection_ip"] == "192.168.10.20", (
        f"Phase 41-09 WR-05: expected connection_ip='192.168.10.20' "
        f"(the TCP dial target), got {envelope.get('connection_ip')!r}."
    )
    assert envelope["hostname"] != envelope["connection_ip"], (
        "Phase 41-09 WR-05: the split is meaningful only when "
        "requested != dial_target. With pve != 192.168.10.20, the two "
        "fields must differ."
    )
