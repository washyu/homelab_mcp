## Summary

Phase 39.1 threads `credential_id` through `_enumerate_proxmox_vms` / `_enum_one` via an Option B side-map, and adds an AST guard to prevent regression. The mechanical fix at `drift_detection.py:430` is correct and the AST guard at `tests/test_ast_regression.py:880` correctly walks `ast.Call` nodes (not source-text regex, per threat model T-39.1-03).

Findings center on two structural concerns the plan acknowledges but does not fully harden:

1. The side-map dict comprehension silently collapses duplicate hostnames in `rows` to "last-row wins" — combined with the cluster-dedupe in `_enumerate_proxmox_vms` (which also picks ONE representative per cluster), there is a narrow case where the surviving representative-hostname's row binding is not the same row that won the cluster-dedupe. The Phase 35 D-14 `store_device` hostname-only match clause makes true duplicates rare in practice, but `host_to_binding`'s last-write-wins is undocumented behavior.
2. The AST guard correctly catches direct-call regressions but the second test (`test_phase39_1_guard_catches_added_helper`) is a tautology of the first when the floor is satisfied — it does not actually verify the guard "catches an added helper" as its name promises.

No security vulnerabilities, no data-loss paths, no crashes. The 7-key `probed_ok` contract is preserved. mypy/ruff hygiene is clean.

## Warnings

### WR-01: Side-map last-write-wins on duplicate hostnames is undocumented

**File:** `src/homelab_mcp/drift_detection.py:1012-1014`
**Issue:** The dict comprehension

```python
host_to_binding: dict[str, str | None] = {
    (row.get("hostname") or ""): row.get("proxmox_credential_id") for row in rows if row.get("hostname")
}
```

silently collapses any duplicate-hostname rows in `rows` to the LAST row's `proxmox_credential_id`. Phase 35 D-14 (`store_device` hostname-only match) reduces but does not eliminate this — a transient race during `discover_and_map` (two concurrent inserts both passing the unique constraint, or a not-yet-purged failed-discovery row sharing a hostname with a fresh row) yields two rows with the same hostname and potentially different `proxmox_credential_id` values. `_bulk_universal_core_probes` already dedupes its input (line 549-556) on hostname before SSH probes — but the new side-map does not, and the cluster-dedupe in `_enumerate_proxmox_vms` (line 425) operates on `(cluster_name OR hostname)` from `pairs`, which can pick a different row's hostname than the side-map's last-write-wins entry. Worst case: `_enum_one` resolves with binding belonging to row A while the surviving hostname belonged to row B's cluster_name dedupe — a quietly-mis-attributed credential.

**Fix:** Either match the dedupe pattern of `_bulk_universal_core_probes` (skip subsequent rows with a hostname already seen) or assert the invariant explicitly. Simplest:

```python
host_to_binding: dict[str, str | None] = {}
for row in rows:
    hostname = row.get("hostname")
    if not hostname or hostname in host_to_binding:
        continue
    host_to_binding[hostname] = row.get("proxmox_credential_id")
```

This matches the "first-write-wins" policy of `_bulk_universal_core_probes` so the side-map and SSH probe map agree on which row each hostname maps to. Add a comment naming the policy explicitly so future contributors can see why.

### WR-02: `test_phase39_1_guard_catches_added_helper` does not test what its name claims

**File:** `tests/test_ast_regression.py:917-940`
**Issue:** The test is named `test_phase39_1_guard_catches_added_helper` and its docstring describes "Defensive: verify the guard ENUMERATES at least 2 call sites." But it does not actually exercise "an added helper" — it only asserts `len(calls) >= 2`. If a future contributor adds a third helper that omits `credential_id=`, the FIRST test (`test_get_proxmox_client_calls_thread_credential_id_phase39_1`) catches that. If they consolidate the two existing call sites into one, this defensive test fires — but the failure message says "if you intentionally consolidated, update this floor or remove the defensive test," which is a meta-instruction to weaken the guard, not evidence the guard caught something. The test is effectively a sanity check that the AST walk discovers calls at all, which the first test already implicitly covers via its `assert calls` precondition at line 892.

**Fix:** Either rename to something like `test_phase39_1_guard_call_site_floor` (matches what it actually does) or strengthen it to actually verify regression-catching, e.g. by AST-rewriting the source to remove `credential_id=` from one call and asserting the first test would fail. The current name promises behavior the test does not deliver, which makes maintenance harder when someone reads the failure message.

### WR-03: AST guard does not cover aliased imports

**File:** `tests/test_ast_regression.py:887-891, 929-933`
**Issue:** The guard matches `ast.Call` where `isinstance(n.func, ast.Name) and n.func.id == "get_proxmox_client"`. This correctly excludes `getattr(...)` indirection (documented in T-39.1-03), but it ALSO silently misses an import alias:

```python
from .proxmox_api import get_proxmox_client as gpc
...
client = await gpc(host=h, session=session)  # guard does not see this
```

`drift_detection.py:42` currently imports unaliased, so this is not a current bug — but the guard's scope docstring (lines 866-873) lists only `getattr` indirection as out-of-scope. An alias rebinding looks identical to a direct call at the AST level (still `ast.Name`), just with a different `func.id`. A future refactor that aliases the import for any reason silently drops the call site from the guard's coverage.

**Fix:** Either (a) add a top-of-file AST check that asserts `get_proxmox_client` is imported under its canonical name in `drift_detection.py` (no `as` clause), or (b) extend the guard to also discover aliases by walking `ast.ImportFrom` nodes and tracking aliased local names. Option (a) is simpler:

```python
imports = [
    a for n in ast.walk(tree)
    if isinstance(n, ast.ImportFrom) and (n.module or "").endswith("proxmox_api")
    for a in n.names if a.name == "get_proxmox_client"
]
assert imports and all(a.asname is None for a in imports), (
    "Phase 39.1 guard: get_proxmox_client must be imported under its "
    "canonical name in drift_detection.py — aliasing would bypass the "
    "ast.Name match below."
)
```

### IN-02: Side-map dict comprehension collapses empty/None hostnames silently

**File:** `src/homelab_mcp/drift_detection.py:1012-1014`
**Issue:** `(row.get("hostname") or "")` is paired with `if row.get("hostname")`, so the `or ""` fallback is unreachable in this comprehension — the filter clause has already excluded falsy hostnames. This is harmless dead defense, but it suggests the author copied the pattern from line 1004 (`sitemap_hostnames`) where `or ""` IS reachable because the filter is on `if row.get("hostname")` AFTER the `(row.get("hostname") or "").lower()`. In the new code, the filter is identical to the truthiness of the key expression, so `or ""` is genuinely dead.

**Fix:** Drop the `or ""` since the filter clause makes it unreachable, or add a comment explaining the redundancy is intentional (matches sitemap_hostnames style for diff readability). Minor; not load-bearing.

```python
host_to_binding: dict[str, str | None] = {
    row["hostname"]: row.get("proxmox_credential_id") for row in rows if row.get("hostname")
}
```
