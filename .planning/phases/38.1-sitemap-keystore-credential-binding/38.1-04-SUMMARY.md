# Plan 38.1-04 Summary — destructive R10 migration + idempotent R2 ALTER

## What was built

`migration.py` now applies the Phase 38.1 destructive drop-and-recreate
exactly once per install, gated on a `~/.homelab_mcp/migration_state.json`
version stamp. Both SQLite and Postgres adapters are covered.

- D-19 idempotency: `_phase_38_1_applied` reads the stamp; second-run is a
  no-op.
- D-20 ordering: archive registry → drop devices → recreate → stamp last.
  Stamp is only written when both backup + drop succeed.
- D-21 three-block stderr banner: action / why / recovery; block 1
  explicitly names BOTH the dropped `devices` table AND the cleared
  `discovery_history` rows (W5).
- D-22 microsecond-precision timestamp on `.bak.<ts>` filename; while-loop
  guards against collisions so existing backups are never overwritten.
- W5: SQLite explicit `DELETE FROM discovery_history` before `DROP TABLE
  devices` (SQLite does not auto-cascade FK on DROP TABLE). Postgres uses
  `DROP TABLE devices CASCADE` for the same effect.
- R2 idempotent `ALTER TABLE ADD COLUMN` for `ssh_credential_id` /
  `proxmox_credential_id`. SQLite uses PRAGMA-guarded `ALTER`; Postgres
  uses native `ADD COLUMN IF NOT EXISTS`. Either path is a no-op when the
  destructive block has just run (CREATE TABLE already includes them) or
  when ALTER ran on a previous startup.

Knock-on fix: extended Phase 35 D-01's `devices_new` schema rebuild to
include `ssh_credential_id` and `proxmox_credential_id` so that the
table-rename dance preserves the binding columns. Without this fix, the
rebuild would silently drop them and Plan 04's idempotent ALTER block
would re-add them on every startup that hits Phase 35 D-01.
