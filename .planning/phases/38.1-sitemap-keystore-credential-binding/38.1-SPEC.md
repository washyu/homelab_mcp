# Phase 38.1: Sitemap-keystore credential binding — Specification

**Created:** 2026-04-26
**Ambiguity score:** 0.116 (gate: ≤ 0.20)
**Requirements:** 10 locked

## Goal

A user who runs the documented happy path — `credentials add --type proxmox <id> <user> <secret>`, then `discover_and_map <id>`, then `scan_infrastructure_drift` — sees their host in `probed_ok` (count ≥ 1), regardless of whether they registered the credential by IP, short hostname, or FQDN. Drift detection becomes verifiable end-to-end in Claude Desktop instead of silently returning `scanned: 0`.

## Background

Claude Desktop UAT on 2026-04-26 surfaced two bugs that nullify v1.7's headline drift outcome:

- **Bug O (architectural).** Sitemap rows store friendly hostnames (`pve`, `truenas`); keyring/registry entries are keyed by IP or FQDN (`192.168.10.20`, `pve1.home`). `resolve_proxmox_credentials(host)` (`proxmox_api.py:194-240`) Tier-1 does exact-match `entries[hostname == host]`, so the names don't bridge. Tier-2 cluster-walk only saves the day if a cluster-scoped credential exists. `drift_detection.py:146-149` then silently skips rows on `CredentialNotFoundError`, returning `scanned: 0` with no user-visible signal. The same hostname-exact-match pattern exists in `resolve_ssh_credentials` (`ssh_tools.py:80-160`).
- **Bug N.** Drift's eligibility heuristic is invisible: nothing in `get_network_sitemap` tells the user which rows will be scanned vs. silently skipped, so users can't even diagnose Bug O from the outside.

Current state of the join surface:

| Surface | Identifier | Stable? |
|---|---|---|
| `devices` row | autoincr `id`; natural key `hostname` | Yes (sitemap-internal) |
| Credential registry entry | composite tuple `(credential_type, hostname, username, scope, cluster_name)` | No — depends on hostname spelling |
| OS keyring entry | `(service_name, "{username}@{hostname}" \| "{username}@cluster:{cluster}")` | No — depends on hostname spelling |

Phase 38 added the fingerprint substrate; Phase 39 builds drift detection cases (DRFT-17/18/19) on top. Phase 39 cannot ship if drift can't reach the hosts to compare against. This phase inserts the missing join layer so v1.7's milestone outcome becomes testable.

## Requirements

1. **Registry UUID identifier**: Every credential registry entry carries an opaque `credential_id` UUID generated at registration time.
   - Current: Entries identified by composite tuple `(credential_type, hostname, username, scope, cluster_name)` in `credential_store.py:175-249`; no opaque ID
   - Target: `register_credential()` generates a UUIDv4 and stores it as `credential_id` in the entry; `unregister_credential()` deletes by UUID; rotation (`remove` then `add` for same hostname/username) produces a fresh UUID
   - Acceptance: Every entry written by `register_credential()` after this phase contains a `credential_id` field matching the UUIDv4 regex; `remove` + re-`add` for the same `(type, hostname, username)` produces two different UUIDs

2. **Sitemap binding columns**: Each `devices` row carries nullable `ssh_credential_id` and `proxmox_credential_id` UUID-string columns on both SQLite and Postgres adapters.
   - Current: `devices` table (`database.py:128-159` SQLite, `database.py:537-565` Postgres) has no credential reference
   - Target: Schema migration adds both columns (SQLite `TEXT`, Postgres `UUID` or `TEXT` for parity) as nullable; existing rows have NULL until rebound
   - Acceptance: Schema migration runs cleanly on fresh + existing DBs for both adapters; rows can persist non-null bindings; `SELECT proxmox_credential_id FROM devices WHERE ...` works in both

3. **Auto-bind at discovery**: `discover_and_map` writes `ssh_credential_id` from the credential it used to connect.
   - Current: Discovery doesn't write any binding
   - Target: When `resolve_ssh_credentials` returns a registry-resolved credential, the resulting sitemap upsert sets `ssh_credential_id` to that entry's UUID
   - Acceptance: After `discover_and_map <hostname>` against a host with a registered SSH credential, `SELECT ssh_credential_id FROM devices WHERE hostname = ?` returns the registry entry's UUID

4. **Auto-bind on `credentials add`**: `credentials add --type {ssh,proxmox} <hostname>` writes the corresponding `*_credential_id` to a matching sitemap row when one exists.
   - Current: `credentials add` (CLI in `cli.py` — needs grep) doesn't touch the sitemap
   - Target: After `register_credential()` succeeds, look up sitemap rows where `hostname == registered_hostname` OR `connection_ip == registered_hostname`; on a single unambiguous match, set `<type>_credential_id` to the new UUID; ambiguous or no-match cases leave the binding null without error
   - Acceptance: Pre-existing sitemap row with `hostname = "192.168.10.20"` + `credentials add --type proxmox 192.168.10.20 root@pam!tok <secret>` → row's `proxmox_credential_id` is non-null afterward; running `add` against an unknown hostname succeeds with binding still null

5. **Resolver short-circuit on `credential_id`**: `resolve_proxmox_credentials` and `resolve_ssh_credentials` accept an optional `credential_id` parameter that bypasses hostname-exact-match.
   - Current: Both resolvers (`proxmox_api.py:194`, `ssh_tools.py:80`) only do hostname-exact-match; mismatch silently fails
   - Target: When caller passes `credential_id`, resolver loads that registry entry by UUID and returns its credential without consulting `hostname`; legacy callers without `credential_id` retain current hostname-exact-match behavior
   - Acceptance: `resolve_proxmox_credentials(host="pve", credential_id=<uuid_for_192.168.10.20_entry>)` returns the token without raising, even though `host != entry.hostname`; same for `resolve_ssh_credentials`

6. **Drift uses binding, never silently skips bound rows**: `drift_detection.py` passes `proxmox_credential_id` to the resolver and routes unbound rows to `not_eligible` instead of dropping them.
   - Current: `drift_detection.py:146-149` calls `get_proxmox_client(host=hostname)` and silently skips on `CredentialNotFoundError`
   - Target: Drift loop reads `row.proxmox_credential_id`; passes it to `get_proxmox_client` / `resolve_proxmox_credentials`; rows with NULL binding land in a new `not_eligible` bucket with a reason field, never silently dropped
   - Acceptance: AST guard: no codepath from `scan_infrastructure_drift` to `continue` without enrolling the row in one of the four buckets (probed_ok, unreachable, not_eligible, unknown — `unknown`/`changed` reserved for Phase 39); a row with `proxmox_credential_id IS NOT NULL` always lands in probed_ok or unreachable

7. **Eligibility surfacing**: Drift response gains `not_eligible` bucket and counts; `get_network_sitemap` per-row output gains `eligibility` field.
   - Current: Drift silently drops rows without Proxmox creds; `get_network_sitemap` exposes nothing about eligibility
   - Target: Drift response adds `not_eligible: list[{hostname, connection_ip, scope, reason}]` and `counts.not_eligible: int`; `get_network_sitemap` row output adds `eligibility: {ssh: bool, proxmox: bool}` reflecting `<type>_credential_id IS NOT NULL`
   - Acceptance: Drift `response.counts.not_eligible == COUNT(*) FROM devices WHERE proxmox_credential_id IS NULL` (after filter); `get_network_sitemap` row's `eligibility.proxmox == (proxmox_credential_id IS NOT NULL)`

8. **Manual link/unlink CLI**: `homelab-mcp credentials link/unlink` for explicit rebinding when auto-bind doesn't fit.
   - Current: No CLI link command
   - Target: `homelab-mcp credentials link <hostname> <credential_id> [--type {ssh,proxmox}]` sets the appropriate `*_credential_id` on the matching sitemap row; `unlink <hostname> --type {ssh,proxmox}` nulls it
   - Acceptance: `link` against a known hostname + valid UUID sets the binding; `unlink` nulls it; both error with actionable messages on unknown hostname or UUID

9. **Rotation nulls bindings**: `credentials remove` nulls any sitemap binding that pointed at the removed UUID.
   - Current: `unregister_credential` doesn't touch the sitemap
   - Target: Before deleting a registry entry, walk sitemap rows and `UPDATE devices SET <type>_credential_id = NULL WHERE <type>_credential_id = <uuid>`
   - Acceptance: A bound row + `credentials remove <hostname>` → row's binding is NULL afterward; row otherwise unchanged

10. **Drop & recreate migration**: Schema migration archives the existing credential registry and drops the `devices` table, requiring users to re-register credentials and re-run `discover_and_map`.
    - Current: Existing registry + devices contain pre-binding state
    - Target: Migration step renames `~/.homelab_mcp/credential_registry.json` to `~/.homelab_mcp/credential_registry.json.bak.<timestamp>` and drops the `devices` table on both adapters; release notes document the required re-registration + re-discovery
    - Acceptance: Post-migration, `credential_registry.json` is absent (or empty), `devices` table contains zero rows, `.bak.<timestamp>` file exists with the prior contents; release notes section explicitly lists the recovery sequence

## Boundaries

**In scope:**
- Registry `credential_id` UUID generation + persistence (`credential_store.py`)
- Two nullable UUID columns on `devices` (SQLite + Postgres) — `ssh_credential_id`, `proxmox_credential_id`
- Auto-bind side-effects in `discover_and_map` (SSH) and `credentials add` (both types)
- Resolver `credential_id` parameter on `resolve_proxmox_credentials` + `resolve_ssh_credentials`
- Drift loop refactor: read binding, route unbound to `not_eligible`, never silently skip bound rows
- Eligibility output: `not_eligible` bucket + counts in drift; `eligibility` field per row in `get_network_sitemap`
- CLI `credentials link / unlink` commands
- Rotation cleanup: `credentials remove` nulls matching sitemap bindings
- Drop & recreate migration with backup of registry JSON
- Both ssh + proxmox credential families covered

**Out of scope:**
- Bug P (null-hostname registry entries) — separate cleanup phase; not blocking drift
- Bug K (empty-string hostname not caught by `purge_failed_discoveries`) — separate cleanup phase; needs validation first
- Bug M (drift guidance branching for "in sitemap, no creds" vs "not in sitemap") — partially addressed by `not_eligible` bucket; finer-grained guidance text deferred
- New MCP tools (`relink_device_credential`, `link`, `unlink`) — CLI-only for this phase to keep the agent surface stable
- "Refuse remove if bound" or "recover UUID on re-add" rotation semantics — clean-slate rotation chosen instead
- JSON-blob binding column or join table schema — two columns chosen for queryability
- Auto-backfill of UUIDs onto legacy registry entries — drop & recreate chosen instead
- Best-effort sitemap auto-link migration — drop & rediscover chosen instead
- Re-keying OS keyring entries by UUID — keyring stays keyed by `username@hostname`; UUID lives in registry/sitemap only

## Constraints

- Both database adapters (SQLite + Postgres) must implement the schema change at parity (Pitfall 4 from Phase 38 RESEARCH)
- Keyring keys (`username@hostname` / `username@cluster:<name>`) MUST NOT change — only the registry JSON and `devices` table grow new fields
- `credential_store.py` must remain free of `homelab_mcp` package imports (CRED-04 circular-import constraint)
- Resolver `credential_id` parameter must be keyword-only and default to None for backward compatibility with existing callers (Phase 36/37 drift code)
- Migration step is one-way and destructive (drop & recreate); release notes must document the re-registration sequence before merge
- AST guard required for the drift-loop "no silent skip" invariant (mirrors Phase 35 D-15 / Phase 36 D-13 pattern)

## Acceptance Criteria

- [ ] **Headline round-trip:** `credentials add --type proxmox 192.168.10.20 root@pam!tok <secret>` + `discover_and_map 192.168.10.20` + `scan_infrastructure_drift` returns `response.counts.probed_ok ≥ 1` for that host
- [ ] **Order-independent:** Same round-trip with `discover_and_map` first then `credentials add` produces the same `probed_ok ≥ 1` result
- [ ] **Identifier-form independence:** Round-trip succeeds when the credential is registered by IP, short hostname, OR FQDN — sitemap stored hostname does not need to match registered hostname spelling
- [ ] Every bound `*_credential_id` on a sitemap row resolves to a current registry entry (no dangling refs after migration, after rotation, after add/remove cycles)
- [ ] AST guard: no codepath in `drift_detection.scan_infrastructure_drift` reaches `continue` without enrolling the row in one of the four buckets
- [ ] `response.counts.not_eligible` in drift output equals the count of sitemap rows with `proxmox_credential_id IS NULL` after filter
- [ ] `get_network_sitemap` row output includes `eligibility.ssh` and `eligibility.proxmox` matching the per-row binding state
- [ ] Pre-existing sitemap row + `credentials add --type proxmox <its_hostname>` → row's `proxmox_credential_id` is non-null afterward (auto-bind side effect)
- [ ] Bound row + `credentials remove <hostname>` → row's binding is NULL afterward, row otherwise unchanged (rotation cleanup)
- [ ] Schema migration runs cleanly on both fresh and existing DBs for SQLite and Postgres adapters
- [ ] Migration archives `credential_registry.json` to `.bak.<timestamp>` and drops `devices` table; release notes document the recovery sequence
- [ ] `homelab-mcp credentials link/unlink` CLI commands work against known hostnames and valid UUIDs; error with actionable messages on unknown inputs
