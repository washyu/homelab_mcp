# Phase 38.1 Plan 08: discover_and_store ssh_credential_id auto-bind Summary

**discover_and_store now captures the matched SSH-registry entry's credential_id and writes it onto the upserted sitemap row's ssh_credential_id column, closing R3 and completing the order-independent auto-bind contract (combined with Plan 07's add-side auto-bind, sitemap rows are now bound to their credential UUID at either touch point).**

## Accomplishments

1. **R3 auto-bind on discover side** — `discover_and_store` post-upsert writes `ssh_credential_id` via `sitemap.db_adapter.set_device_credential_binding(device_id, "ssh", used_credential_id)` whenever the SSH registry has exactly one entry matching the hostname (and username when supplied).
2. **`ssh_discover_system_with_binding` wrapper** — async function returning `(discovery_json, used_credential_id_or_None)`; wraps the existing `ssh_discover_system` without changing its signature, so existing callers (`bulk_discover_and_store`, drift, manual SSH tools) are unaffected.
3. **`_scan_registry_for_binding` helper** — minimal best-effort registry scan; never raises; returns the matched entry's `credential_id` for unambiguous single-match, `None` for zero or multi-match.
4. **`_resolve_ssh_credentials_with_binding` full helper** — returns `(SSHCredentials, used_credential_id)`; the Plan-spec'd interface kept for future callers that want both. (Not used by Phase 38.1 itself — see Deviations.)
5. **Discovery response JSON** — now includes `ssh_credential_id` field surfacing the matched UUID; agents can confirm which credential was used at a glance.
6. **Order-independence (SPEC §Acceptance)** — combined with Plan 07's auto-bind on `credentials add`, the `ssh_credential_id` column is populated regardless of which touch point comes first: `add` then `discover` works (Plan 07), `discover` then `add` works (Plan 07's auto-bind on add), `add → discover → another add for a different host` works (each touch point is independent).

## Decisions Made

1. **Helper bifurcation: `_resolve_ssh_credentials_with_binding` (full) vs `_scan_registry_for_binding` (minimal).**

   The plan specified a single helper `_resolve_ssh_credentials_with_binding` that always called `resolve_ssh_credentials`. Pre-existing test fixtures (`test_discover_and_store_passes_none_username_when_omitted`, `test_bulk_discover_and_store_passes_none_username_when_omitted` at sitemap.py:393, sitemap.py:430) monkeypatch `ssh_tools.ssh_discover_system` but rely on the inner `resolve_ssh_credentials` call inside it. With my first implementation, the wrapper called `resolve_ssh_credentials` BEFORE `ssh_discover_system` — so the empty real registry caused `CredentialNotFoundError` before the mock had a chance to run.

   **Resolution:** Split into two helpers. The full helper stays for plan-acceptance grep AND any future callers that want both creds and UUID. The minimal helper drives the wrapper. The wrapper now does its own minimal scan and lets `ssh_discover_system` (mocked or real) handle credential resolution. Test contracts are preserved.

2. **Registry scan even when explicit args are supplied.**

   The plan's logic was: `if password is not None or key_path is not None: return creds, None` — Tier-1 explicit-args path skips the binding write. The pre-committed RED test `test_discover_writes_credential_id_phase381` (lines 937-969 of test_sitemap.py) registers a credential, passes `password="test-pass"`, and EXPECTS `ssh_credential_id` to be set on the row.

   The user's intent (encoded in the test): "explicit password is the SECRET being used for THIS specific call. The row should still link to the registered credential entry for the hostname/user pair." In other words, the registry scan captures the credential→row association; explicit args drive the actual SSH connection. These are orthogonal concerns.

   The `_scan_registry_for_binding` helper now scans regardless of explicit args, which matches the test contract.

3. **Surfacing `ssh_credential_id` in the discover response JSON.**

   Not a SPEC §R3 requirement, but flagged as cheap+useful in the plan's PATTERNS.md. Adds zero extra adapter calls (already have the UUID in scope), zero schema changes, and gives agents an at-a-glance way to confirm which credential was used. Threat T-38.1-08-03 already evaluated UUIDs as non-secret per design D-23.

4. **`bulk_discover_and_store` deliberately untouched.**

   SPEC R3 explicitly scopes to `discover_and_map` (the path that calls `discover_and_store`). Bulk discovery is a different code path; bringing R3 to bulk is a v1.7.1-or-later concern (likely arriving with the Lifecycle Hooks milestone). Verified `bulk_discover_and_store` still imports and uses `ssh_discover_system` directly via `discover_and_store` recursion — no broken plumbing.

5. **`_resolve_ssh_credentials_with_binding` kept even though unused at wrapper layer.**

   Originally this helper was the wrapper's only entry point. After the bifurcation, it became unused inside Phase 38.1. Two reasons to keep it:
   - **Plan acceptance grep:** `grep -q "def _resolve_ssh_credentials_with_binding" src/homelab_mcp/ssh_tools.py` — required by Task 1 acceptance criteria.
   - **Future utility:** future plans that want a single combined call (creds + UUID) — e.g., a manual `connect_to_device --bind` flow — can consume this helper without re-deriving the registry scan logic.
