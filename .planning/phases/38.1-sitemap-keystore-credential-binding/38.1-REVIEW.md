# Phase 38.1: Code Review Report

**Reviewed:** 2026-04-27
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Phase 38.1 introduces UUID-based credential binding between sitemap rows and the keyring registry, replacing the v1.7 silent-skip behavior with a five-bucket drift envelope and explicit `not_eligible` reason routing. Wave 2's Tier-0 UUID short-circuit in both resolvers is well-formed, with defensive UUID validation, type-mismatch checks, and reason_hint propagation. The typed adapter methods (`find_devices_by_hostname_or_ip`, `bulk_null_credential_binding`, `set_device_credential_binding`) successfully encapsulate SQLite-vs-Postgres placeholder differences (Blocker B2 mitigation), and server.py now contains zero raw `?` / `%s` placeholders.

However, the destructive R10 migration has multiple correctness defects that will manifest as data loss or operator confusion: the migration runs on every fresh install (dropping a table init_schema just created and printing an alarming banner), recovery from a deleted state file silently re-runs the destructive block, and the Postgres path's banner falsely claims to clear discovery_history rows when CASCADE only drops the FK constraint. The credentials remove per-node path also has a scope-confusion edge case where a legacy/buggy registry entry with non-empty hostname AND `scope=cluster` would be mismatched, leaving an orphaned keyring secret.

A `_resolve_ssh_credentials_with_binding` helper exists purely to satisfy a plan-acceptance grep and is unreachable code per the Phase 38.1-08 SUMMARY. The drift `not_eligible` bucket routing is correct for Tier-0 paths, but the second `resolve_proxmox_credentials` call on success duplicates work without observable benefit beyond cache-hit telemetry.

## Critical Issues

### CR-01: Destructive Phase 38.1 migration runs on every fresh install — drops a table init_schema just created and prints alarming banner

**File:** `src/homelab_mcp/migration.py:194-217` (SQLite), `src/homelab_mcp/migration.py:504-514` (Postgres)
**Issue:** `_phase_38_1_applied()` returns `False` when the migration state file is missing, which is the case on every fresh install. The flow is:
1. `init_schema` runs `CREATE TABLE IF NOT EXISTS devices (...)` — table created with all binding columns.
2. `init_schema` calls `run_sqlite_migrations(_connection=...)`.
3. The Phase 38.1 R10 block fires unconditionally because no state file exists yet.
4. `DELETE FROM discovery_history` (no rows on fresh install — fine).
5. `DROP TABLE IF EXISTS devices` — drops the table init_schema just created.
6. `cursor.executescript(_SQLITE_RECREATE_DEVICES)` — recreates the same table.
7. Banner prints "Dropped devices table (v1.7 credential-binding rollout)" to stderr — **false statement on fresh installs**, no pre-existing table was dropped.
8. State file written.

This wastes work (drop + recreate of a just-created table) and floods stderr on every first-run with a destructive-sounding banner. Worse, if the state file is later deleted (system migration, accidental cleanup), the destructive block re-fires on next startup, dropping the live `devices` table and clearing `discovery_history` — silent data loss.

The gate should also check whether the binding columns already exist on the live `devices` table. If both `ssh_credential_id` and `proxmox_credential_id` columns are present, the migration is structurally complete and the destructive block should short-circuit even without a state file.

**Fix:**
```python
if not _phase_38_1_applied():
    # Defense-in-depth: only fire the destructive block when the binding
    # columns are actually missing. Protects against state-file deletion
    # silently triggering data loss on a fully-migrated DB.
    cursor.execute("PRAGMA table_info(devices)")
    existing_columns = {row[1] for row in cursor.fetchall()}
    devices_table_exists = bool(existing_columns)
    bindings_already_present = (
        "ssh_credential_id" in existing_columns
        and "proxmox_credential_id" in existing_columns
    )
    if devices_table_exists and bindings_already_present:
        # Already migrated (state file lost or never written) — just stamp.
        _stamp_migration(_PHASE_38_1_KEY)
    elif not devices_table_exists:
        # Fresh install — init_schema just created an empty table; nothing
        # to drop. Skip the banner and just stamp.
        _stamp_migration(_PHASE_38_1_KEY)
    else:
        # Real migration: pre-existing table without binding columns.
        backup_path = _archive_registry_for_phase_38_1()
        cursor.execute("DELETE FROM discovery_history")
        cursor.execute("DROP TABLE IF EXISTS devices")
        conn.commit()
        cursor.executescript(_SQLITE_RECREATE_DEVICES)
        conn.commit()
        _stamp_migration(_PHASE_38_1_KEY)
        applied_migrations.append("phase_38_1_drop_recreate")
        _print_phase_38_1_banner(backup_path)
```

Apply the equivalent guard to `run_postgres_migrations` using `information_schema.columns` to detect the binding columns.

### CR-02: Postgres destructive migration banner lies — DROP TABLE CASCADE does NOT clear discovery_history rows

**File:** `src/homelab_mcp/migration.py:506`, banner text at `src/homelab_mcp/migration.py:78-80`
**Issue:** The Postgres path executes `DROP TABLE IF EXISTS devices CASCADE`. In Postgres, `CASCADE` on `DROP TABLE` cascades to **dependent objects** (foreign-key constraints, views, sequences) — NOT to rows in dependent tables. The `discovery_history` rows survive the drop with their `device_id` FK constraint silently removed; rows then dangle pointing at a regenerated `devices.id` sequence. After re-discovery repopulates `devices` with new SERIAL ids, those orphaned `discovery_history` rows now point at unrelated devices' IDs (potentially), which is a worse failure mode than orphaned rows alone.

The banner explicitly states "Cleared discovery_history rows (FK-dependent on devices table)" — **false on the Postgres path**. The SQLite path explicitly `DELETE FROM discovery_history` first; the Postgres path relies on CASCADE without the equivalent DELETE.

**Fix:**
```python
if not _phase_38_1_applied():
    backup_path_pg = _archive_registry_for_phase_38_1()
    # Mirror SQLite path: clear FK-dependent rows BEFORE dropping the
    # parent. CASCADE on DROP TABLE removes the FK constraint, not the
    # dependent rows — they would otherwise dangle with stale device_ids.
    cursor.execute("DELETE FROM discovery_history")
    cursor.execute("DROP TABLE IF EXISTS devices CASCADE")
    conn.commit()
    cursor.execute(_POSTGRES_RECREATE_DEVICES)
    conn.commit()
    _stamp_migration(_PHASE_38_1_KEY)
    applied_migrations.append("phase_38_1_drop_recreate")
    _print_phase_38_1_banner(backup_path_pg)
```

### CR-03: `_cmd_credentials_remove` per-node path silently leaks keyring secret for legacy/buggy cluster entries with non-empty hostname

**File:** `src/homelab_mcp/server.py:918,936-937`
**Issue:** The per-node remove flow filters registry entries by `e["hostname"] == hostname` only — no `scope` check. If the registry contains a legacy or hand-edited cluster entry where `hostname` was set to a non-empty value (e.g., from a pre-Phase-34 install or a manual edit), `credentials remove <hostname>` (no `--scope`) will:

1. Match that cluster entry in `entries` (line 918).
2. Capture its UUID for cleanup.
3. Call `delete_credential(entry["hostname"], entry["username"], credential_type=credential_type)` with **default `scope="node"`** — but the secret was stored under the cluster keyring key (`f"{username}@cluster:{cluster_name}"`). The keyring lookup uses the wrong key and silently returns `False` (no entry to delete).
4. Call `unregister_credential(hostname, ...)` which removes the registry entry by hostname match.

End state: registry entry gone, sitemap binding nulled, **keyring secret orphaned forever**. No error, no warning — pure silent data leak in the user's OS keyring.

**Fix:** Branch on `entry.get("scope", "node")` when building the delete loop, OR explicitly skip cluster entries during per-node removal:
```python
entries = [
    e
    for e in list_credentials(credential_type=credential_type)
    if e["hostname"] == hostname and e.get("scope", "node") == "node"
]
```
Apply the same defense in the cluster-scope path (filter additionally on `scope == "cluster"`, which it already does — fine).

### CR-04: Tier-0 resolver short-circuits when env-var credentials are set, silently ignoring sitemap binding

**File:** `src/homelab_mcp/proxmox_api.py:459-462`
**Issue:** `get_proxmox_client` only calls `resolve_proxmox_credentials(credential_id=credential_id)` when `host and not api_token and not (username and password)`. If the user has `PROXMOX_USER` + `PROXMOX_PASSWORD` env vars set (or `PROXMOX_API_TOKEN`), `credential_id` is silently dropped and the env-var credentials are used instead.

This breaks the binding contract: a sitemap row with `proxmox_credential_id="<uuid>"` running in an env with `PROXMOX_USER` set will use env credentials, never validating that the bound credential still exists. Worse, scan_drift's whole `not_eligible` reason routing depends on the resolver actually being invoked — under env-var dominance, every probe succeeds (using env creds) regardless of binding state, and stale bindings become invisible to drift.

The "preserves SC-5 back-compat" comment suggests this is intentional, but it directly subverts the architectural fix for Bug O. At minimum, when `credential_id is not None` AND env-var creds are present, the code should emit a `logger.warning` so operators can detect the override.

**Fix:**
```python
if host:
    has_explicit_auth = bool(api_token or (username and password))
    if credential_id is not None and has_explicit_auth:
        logger.warning(
            "Sitemap binding %s ignored for host=%s — explicit/env-var "
            "credentials take precedence. Drift reports against env-creds, "
            "not the bound UUID.",
            credential_id,
            host,
        )
    if not has_explicit_auth:
        resolved_token, scope, cluster_name = await resolve_proxmox_credentials(
            host, session=session, credential_id=credential_id,
        )
        api_token = resolved_token
        ...
```
Document the precedence rule explicitly in the docstring, and add a regression test asserting the warning fires.

### WR-01: `_resolve_ssh_credentials_with_binding` is dead code retained only for plan-acceptance grep

**File:** `src/homelab_mcp/ssh_tools.py:304-382`
**Issue:** Per `38.1-08-SUMMARY.md`, this helper was kept "to satisfy the plan's acceptance grep." It contains its own (now-redundant) registry scan, calls `resolve_ssh_credentials`, and returns a tuple. Leaving dead helpers in the public surface is a maintenance hazard — future readers will assume it's the canonical path and reach for it, only to discover the wrapper bypasses it.

**Fix:** Either delete the helper and update the SUMMARY rationale, or add a module-level `# DEAD CODE: kept solely for plan-acceptance grep — DO NOT USE` comment immediately above the def with a pointer to the actual wrapper.

### WR-02: SQLite `bulk_null_credential_binding` will hit SQLite's max-parameters limit on large rotations

**File:** `src/homelab_mcp/database.py:475`
**Issue:** `placeholders = ",".join("?" * len(credential_ids))` constructs an `IN (?,?,...)` clause with one placeholder per UUID. SQLite's default `SQLITE_MAX_VARIABLE_NUMBER` is 999 (and 32766 on newer builds). A user with thousands of bound rows (one cluster credential serving 1000+ nodes via manual `link`) running `credentials remove` would crash with `sqlite3.OperationalError: too many SQL variables`.

In practice, `null_bindings_for_credential_id` is called per-UUID (single-element list), so this is bounded by the number of registry entries removed at once — typically 1 for per-node, ≤2 for cluster. Hard to hit in practice, but the abstraction promises bulk and is brittle for large lists.

**Fix:** Chunk the UUID list into batches of 500 inside `bulk_null_credential_binding`, or document the per-call upper bound in the docstring.

### WR-03: `_archive_registry_for_phase_38_1` returns synthetic `.bak.none` path that doesn't exist — banner misleads

**File:** `src/homelab_mcp/migration.py:55-56,77`
**Issue:** When the registry file is absent, the function returns `pathlib.Path(str(_REGISTRY_PATH) + ".bak.none")` without creating the file. The banner then prints `"Archived credential registry to /home/user/.homelab_mcp/credential_registry.json.bak.none"` — no file was actually archived. Operators looking for the backup will be confused.

**Fix:** When the registry doesn't exist, return `None` from the helper and gate banner block 1 to only print the "Archived..." line when a real backup happened:
```python
def _archive_registry_for_phase_38_1() -> pathlib.Path | None:
    from .credential_store import _REGISTRY_PATH  # noqa: PLC0415
    if not _REGISTRY_PATH.exists():
        return None
    # ... rest unchanged
```
Update `_print_phase_38_1_banner` to skip the "Archived..." line when `backup_path is None`.

### WR-04: Drift's second `resolve_proxmox_credentials` call on success duplicates Tier-0/Tier-1/Tier-2 logic

**File:** `src/homelab_mcp/drift_detection.py:271-273`
**Issue:** After `get_proxmox_client` succeeds, the code calls `resolve_proxmox_credentials` a second time purely to capture `(scope, cluster_name)` for telemetry. The comment says "second resolver call hits `_HOST_CLUSTER_CACHE` so cost is microseconds" — true for Tier-2 cluster-walk results, but Tier-0 (UUID short-circuit) and Tier-1 (per-node) re-execute the entire `find_credential_by_id` / `list_credentials` + `get_credential` flow including a keyring round-trip, which on some headless Linux configurations is non-trivial (D-Bus probe latency).

The defensive `try/except CredentialNotFoundError` block on lines 274-284 routes to `not_eligible` if the second call raises. This means **a flaky keyring** (succeeds first call, fails second) would route a host to `not_eligible` with `keyring_desync` reason even though `/cluster/status` was already successfully probed. The host appears unreachable to operators when it's actually fine.

**Fix:** Modify `get_proxmox_client` to return the resolution telemetry alongside the client (e.g., return a tuple or attach as attributes on the client), or cache the (scope, cluster_name) inside `_HOST_CLUSTER_CACHE` for all tiers, not just cluster-walk hits. Avoids the double-call entirely.

### WR-05: `find_devices_by_hostname_or_ip` Postgres implementation may mismatch `INET` rows stored with CIDR notation

**File:** `src/homelab_mcp/database.py:984-988`
**Issue:** The query is `WHERE hostname = %s OR connection_ip::text = %s`. Postgres `INET` columns can store either a bare address (`192.168.1.5`) or a CIDR-suffixed address (`192.168.1.5/32`). The cast preserves whatever was stored. If `store_device` ever inserts a value with a netmask suffix, exact-string match against a bare IP will silently miss the row — and auto-bind will think there's no matching sitemap row, falling into the silent-no-op D-01 path.

`store_device` (database.py:863) inserts `device_data["connection_ip"]` as-is; the producer in `ssh_tools.py:771` writes a bare IP, so today this is fine. But it's brittle — any future producer that captures the network mask breaks auto-bind silently.

**Fix:** Compare against `host(connection_ip)` instead of the cast:
```sql
WHERE hostname = %s OR host(connection_ip) = %s
```
`host()` strips any netmask suffix. Also add a regression test asserting auto-bind works when the row was inserted with `192.168.1.5/24`.

### WR-06: Destructive migration banner spam on every test run with `:memory:` DBs

**File:** `src/homelab_mcp/migration.py:217,514`
**Issue:** Tests that instantiate `SQLiteAdapter(":memory:")` per-test trigger the destructive migration block on every test (no state file exists for an in-memory DB). The banner prints to stderr on every test, degrading test output readability and adding noise to CI logs. It also runs the drop+recreate sequence per test, slowing down the suite.

### WR-07: `_cmd_credentials_add` cluster path discards the returned `credential_id`

**File:** `src/homelab_mcp/server.py:728-735`
**Issue:** `register_credential(...)` now returns the UUIDv4. The per-node path captures it for auto-bind (line 783), but the cluster-scope branch (line 728) calls `register_credential` without capturing the return value. By design (D-07: cluster credentials don't auto-bind), but the success print message ("Stored proxmox credential for user@cluster:foo") doesn't include the UUID — operators must run `credentials list --json` separately to discover it for `link` operations.

Optional but improves the link workflow significantly.

### WR-08: `_classify_credential_failure` falls through to `binding_stale` when reason_hint is missing — masks real Tier-1/Tier-2 failures

**File:** `src/homelab_mcp/drift_detection.py:81-84`
**Issue:** When `binding is not None` but the resolver raised without setting `reason_hint` (e.g., a Tier-1 path raised `CredentialNotFoundError` — possible in Phase 38.1 only via an in-test fake or future code), the function returns `"binding_stale"` as a defensive default. This is documented but masks a real edge: a row whose binding column is set BUT whose Tier-0 short-circuit returned an entry that then failed Tier-2 cluster-walk would be reported as `binding_stale` when the actual cause was network/probe failure. The user's recovery action ("re-add credential") wouldn't fix it.

The Tier-0 paths in Wave 2 do consistently set `reason_hint`, so this is theoretical today. But the fall-through erases information.

**Fix:** When `hint` is missing but `binding is not None`, log a `logger.warning` that we're defaulting:
```python
logger.warning(
    "Resolver raised CredentialNotFoundError without reason_hint for "
    "bound row (binding=%s). Defaulting to binding_stale; this indicates "
    "a code path that should set reason_hint explicitly.",
    binding,
)
return "binding_stale"
```

### WR-09: Phase 38.1 R10 migration runs `DELETE FROM discovery_history` without checking the table exists

**File:** `src/homelab_mcp/migration.py:202`
**Issue:** The destructive block runs `cursor.execute("DELETE FROM discovery_history")` unconditionally. Today `init_schema` always creates this table before migrations run, so it should always exist. But if a future refactor moves the migration call before `CREATE TABLE`, this breaks. Defense-in-depth: guard the DELETE on table existence.

**Fix:**
```python
cursor.execute(
    "SELECT name FROM sqlite_master WHERE type='table' AND name='discovery_history'"
)
if cursor.fetchone():
    cursor.execute("DELETE FROM discovery_history")
cursor.execute("DROP TABLE IF EXISTS devices")
```

## Info

### IN-01: `register_credential` returns a UUID even when `_save_registry` could partially fail

**File:** `src/homelab_mcp/credential_store.py:246-259`
**Issue:** The function generates a UUID, appends it to `entries`, calls `_save_registry`, then returns. If `_save_registry`'s `write_text` raises (disk full, permission denied), the exception propagates but the caller has no UUID and the registry is in an indeterminate state. `_save_registry` is a one-line wrapper; modern atomic-write would use `os.replace` after a temp-file write to avoid partial-write corruption.
**Fix:** Use atomic write in `_save_registry`:
```python
def _save_registry(entries: list[dict[str, str]]) -> None:
    _REGISTRY_PATH.parent.mkdir(parents=True, exist_ok=True)
    tmp = _REGISTRY_PATH.with_suffix(".json.tmp")
    tmp.write_text(json.dumps(entries, indent=2))
    tmp.replace(_REGISTRY_PATH)  # atomic on POSIX
```

### IN-03: `set_device_credential_binding` server-module wrapper does redundant lookup

**File:** `src/homelab_mcp/server.py:553-563`
**Issue:** The wrapper calls `find_devices_by_hostname_or_ip(hostname)`, filters to exact hostname match, then calls the adapter's `set_device_credential_binding(matches[0]["id"], ...)`. Callers (`_cmd_credentials_link`, `_cmd_credentials_unlink`) have already done the same lookup themselves and pass `rows[0]["hostname"]`, causing a second identical query. Performance issue (out of v1 scope) and potential race window between the two lookups.
**Fix:** Accept `device_id` directly in the server-module wrapper and let callers pass `rows[0]["id"]`:
```python
def set_device_credential_binding_by_id(
    device_id: int, credential_type: str, credential_id: str | None
) -> None:
    sitemap = NetworkSiteMap()
    sitemap.db_adapter.set_device_credential_binding(
        device_id, credential_type, credential_id,
    )
```

### IN-04: `find_credential_by_id` does linear scan — O(n) per resolve call

**File:** `src/homelab_mcp/credential_store.py:327-330`
**Issue:** Each Tier-0 resolution scans the entire registry list. For a homelab with <50 entries this is fine, but every drift scan iterates all sitemap rows and each row's resolver triggers a registry load + linear scan. On a 100-row sitemap with 50 registry entries, that's 5000 dict comparisons per scan. Out of v1 scope per the review charter.
**Fix:** Cache the registry as a `dict[credential_id, entry]` keyed by UUID inside `_load_registry`. Or accept the cost given homelab scale.
