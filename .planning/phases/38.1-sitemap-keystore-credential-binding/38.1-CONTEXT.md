# Phase 38.1: Sitemap-keystore credential binding — Context

**Gathered:** 2026-04-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Insert a missing join layer between sitemap rows and keyring/registry entries so drift detection can reach Proxmox/SSH hosts regardless of which name spelling the credential was registered under (IP, short hostname, FQDN). An opaque `credential_id` UUID binds each `devices` row to its credential entry; the resolver short-circuits on UUID instead of hostname-exact-match; drift surfaces unbindable rows in a `not_eligible` bucket instead of silently skipping them. Closes Bug O (architectural credential resolution gap) and Bug N (invisible eligibility) from the 2026-04-26 Claude Desktop UAT.

</domain>

<decisions>
## Implementation Decisions

### Auto-bind ambiguity policy

- **D-01:** Canonical workflow is `credentials add` → `discover_and_map` → `scan_infrastructure_drift`. No matching sitemap row at `add` time is the EXPECTED state — silent (no error, no warning, just `Stored ... credential for ...`). User-driven principle.
- **D-02:** Keep `hostname` as the registry's natural-key field. SSH+Proxmox overlap on the same host is handled cleanly by separate `credential_type` keying and the two-column binding. Friendly-name rename deferred to v1.8 backlog.
- **D-03:** Credential `hostname` field is an opaque label — accept any string (IP, short name, FQDN). Auto-bind matches on `hostname == registered_hostname OR connection_ip == registered_hostname`. Multi-match is rare (a sitemap-side data-quality issue).
- **D-04:** Single-match WITH existing non-null binding (overwrite case): interactive prompt using hostname only, no UUIDs in user-facing text. Prompt: `Sitemap row "<hostname>" is already bound to a different <type> credential. Overwrite the mapping? [y/N]:`. Credential is still stored regardless of the answer.
- **D-05:** Non-TTY behavior on overwrite/multi-match prompt: skip the bind, print warning, exit 0. Default-safe; no surprise rebinds in unattended scripts. Credential is still stored.
- **D-06:** Multi-match (>1 sitemap row matches): interactive prompt with numbered hostname choices.
  ```
  Multiple sitemap rows match "192.168.10.20":
    [1] pve (ip=192.168.10.20)
    [2] 192.168.10.20 (ip=192.168.10.21)
    [s] skip auto-bind
  Which row should this credential bind to?
  ```
  Hostnames only — no UUIDs. Non-TTY → skip + warn.
- **D-07:** Cluster-scope `credentials add --scope cluster:<name>` skips auto-bind entirely. `proxmox_credential_id` stays NULL on cluster-served rows; drift's resolver Tier-2 cluster walk still resolves them at scan time.

### `not_eligible` shape + sitemap eligibility field

- **D-08:** `not_eligible[].reason` is a small enum + companion `message` field for the human sentence. Codes (final list, post-AST-area refinement):
  - `unbound` — no `<type>_credential_id` set
  - `keyring_desync` — binding UUID exists but keyring lookup returned None
  - `binding_stale` — UUID points at a registry entry that no longer exists
  - `degenerate` — sitemap row has degenerate hostname (`None`, `""`, `"unknown"`, or `status="error"`); see D-17
  Shape: `{reason: "unbound", message: "No proxmox credential bound; run \`credentials add --type proxmox <hostname>\` to bind."}`.
- **D-09:** Cluster-served rows (binding NULL but a cluster credential resolves them via Tier-2 walk): drift's loop reads the binding; if NULL, it still calls `resolve_proxmox_credentials(hostname)` which does the Tier-2 cluster walk. Success → `probed_ok` / `unreachable` normally (NOT `not_eligible`). Hard failure → `not_eligible` with `reason="unbound"`. SPEC acceptance criterion for `counts.not_eligible` needs revision: equals `COUNT(*) WHERE proxmox_credential_id IS NULL AND no cluster credential resolves the row` (after filter). `eligibility.proxmox` on `get_network_sitemap` still reflects binding-state only (false for cluster-served rows).
- **D-10:** `eligibility` field shape on `get_network_sitemap` rows is the SPEC-literal bool pair: `{ssh: bool, proxmox: bool}`. `true` when `<type>_credential_id IS NOT NULL`, `false` otherwise. Pure binding-state — no resolver runs at sitemap-read time. Agent runs `credentials list` for richer detail.

### Resolver `credential_id` mismatch behavior

- **D-11:** When `resolve_*_credentials(host, credential_id=<uuid>)` is called and the UUID is NOT in the registry (stale binding), the resolver raises `CredentialNotFoundError` with a clear `binding stale: UUID <x> not in registry` message. **Never falls back** to hostname-exact-match — that would mask rotation cleanup bugs (the same silent-skip class we're closing). Drift catches the exception and routes the row to `not_eligible` with `reason="binding_stale"`.
- **D-12:** When the UUID lookup HITS a registry entry but the keyring secret returns None (desync), the resolver raises `CredentialNotFoundError` with the desync warning shape (mirrors `proxmox_api.py:228-236`). Drift maps this case to `not_eligible` with `reason="keyring_desync"`. Same exception class as D-11 — drift differentiates via context (was a credential_id passed? did the registry-lookup return an entry?), not via exception subclass.
- **D-13:** When both `credential_id=<uuid>` AND `host` are passed, and the UUID's entry has a `hostname` field that doesn't match `host`: **UUID wins, host is ignored** for lookup purposes. This is the whole point of the binding (sitemap stores `pve`, registry stores `192.168.10.20`; UUID bridges them). The mismatch is the EXPECTED case, not an error. Host stays useful for log/error message context.
- **D-14:** Both resolvers (`resolve_proxmox_credentials`, `resolve_ssh_credentials`) gain `credential_id` as a **keyword-only parameter, default `None`**. Existing positional callers keep working unchanged. Matches the `session=` keyword-only pattern already on `resolve_proxmox_credentials`. Required by SPEC constraint.

### AST guard pattern for `no silent skip`

- **D-15:** The AST guard's shape is "**forbid every `continue` inside the row-loop body of `scan_infrastructure_drift`**". The walker locates the for-loop in `drift_detection.scan_infrastructure_drift`, finds every `ast.Continue` node within its body, and fails CI if any are present. Forces every code path to fall through to a bucket append. Catches the exact pattern from `drift_detection.py:148-149` (the original Bug O shape).
- **D-16:** Guard scope is **only `scan_infrastructure_drift` for now** (matches Phase 35 D-15's targeted scope). Phase 39's unknown/changed detection helpers will likely extend the guard's target list when they land. Easier to extend than to retrofit overly broad coverage.
- **D-17:** The existing degenerate-row filter at `drift_detection.py:142-143` (`if hostname is None or hostname in ("", "unknown") ...: continue`) is **converted to bucket routing** — degenerate rows land in `not_eligible` with the new `reason="degenerate"` enum value (D-08). No allowlist, no AST exemption. Operator sees the bad rows in eligibility output instead of them being invisible — better UX. Slight semantic shift from current behavior; flagged in the planner's risk list.
- **D-18:** Add a **functional regression test alongside the AST guard**. Test fixture: 1 sitemap row with NULL `proxmox_credential_id` + 1 row with a bound UUID + (optionally) 1 degenerate row. Run `scan_infrastructure_drift`. Assert: NULL row appears in `not_eligible` with `reason="unbound"`; degenerate row appears in `not_eligible` with `reason="degenerate"`; bound row appears in `probed_ok` or `unreachable`; no row vanishes. AST guard catches structural regression; functional test catches semantic routing bugs.

### Migration banner + ordering

- **D-19:** Migration is **startup-fired with a version-stamp guard**. A marker (e.g., `~/.homelab_mcp/migration_state.json` recording `phase_38_1_applied: true` + timestamp) gates the destructive steps. Idempotent: re-runs are no-ops once stamped. Matches the existing `run_sqlite_migrations` pattern. No extra command for the user to remember.
- **D-20:** Order of operations: **(1) backup registry → (2) drop devices table → (3) stamp version**. Registry archive happens first (preserves user data on disk); devices table drops second (sitemap is rebuildable from re-discovery, less precious); stamp last. If step 2 fails, the stamp isn't written, so re-run picks up where it left off (and a fresh timestamp on the next backup, per D-22).
- **D-21:** User-visible banner is **multi-line stderr output with recovery steps inline**, mirroring the v1.6 `ssh_credentials` drop banner at `migration.py:54-62`. Three blocks:
  1. **What happened** — `Archived credential registry to ~/.homelab_mcp/credential_registry.json.bak.<ts>` and `Dropped devices table (v1.7 credential-binding rollout)`.
  2. **Why** — `v1.7 introduces opaque credential UUIDs binding sitemap rows to keyring entries. Existing registry entries don't carry UUIDs and the devices table doesn't carry binding columns; clean-slate is required.`
  3. **Recovery (copy-paste ready)** — concrete commands: `homelab-mcp credentials add --type {ssh,proxmox} <hostname> <username>` and `homelab-mcp discover_and_map <hostname>`.
- **D-22:** When `.bak.<timestamp>` already exists (partial upgrade, downgrade, retry), **always use a fresh timestamp; never overwrite**. Each migration attempt gets its own backup file. Disk litter is small (registry JSON is KB-scale). Idempotency comes from the version stamp (D-19), not from the bak filename.

### `link/unlink` CLI shape + UUID surfacing

- **D-23:** UUIDs surface in **`credentials list --json` only**. Default tabular `credentials list` stays UUID-free (matches D-04/D-06's "no UUIDs in user-facing text" principle). The `--json` flag emits each entry with its `credential_id`. Power users / agents copy from there.
- **D-24:** `credentials link` accepts **UUID only** — single-shape API: `credentials link <sitemap_hostname> <credential_id> --type {ssh,proxmox}`. No auto-detect, no hostname-tuple alias. SPEC R8 verbatim. The `--json` discoverability path (D-23) closes the UX gap.
- **D-25:** `credentials link` **validates that the supplied `credential_id` belongs to an entry whose `credential_type` matches `--type`**. Mismatched type → actionable error: `credential <uuid> is type=ssh, but --type proxmox was requested. Pass --type ssh, or use a proxmox credential.` Catches a real footgun (the binding is type-keyed: `<type>_credential_id`).
- **D-26:** When `credentials remove <hostname>` nulls sitemap bindings (SPEC R9 rotation cleanup), the CLI **prints the affected rows on stderr**, hostnames only: `Unlinked sitemap row(s): <hostname1>, <hostname2>`. If zero rows were bound, print nothing or a quiet `No sitemap bindings to clean up.` Matches the `Stored ... credential for ...` style of single-line stderr feedback.

### Claude's Discretion

- UUID library: stdlib `uuid.uuid4()` is the obvious default (no new dependency, RFC 4122 compliant, matches Python ecosystem norms). Planner may choose `uuid7` only if there's a strong motivation; default is `uuid4`.
- Version-stamp file format: JSON in `~/.homelab_mcp/migration_state.json` with field naming aligned to the existing `~/.homelab_mcp/credential_registry.json` style. Specific schema is planner's call.
- Exception-to-reason mapping in drift: planner decides whether drift inspects exception messages, uses sentinel return shapes, or wires a small helper that maps `(exception, context)` → `not_eligible.reason`. The four reasons (D-08) are locked; the wiring is implementation detail.
- Acceptance test fixtures for the schema migration (drop & recreate path): planner picks Docker integration test, `:memory:` SQLite, or `tmp_path`-based file SQLite based on existing test conventions.

</decisions>

Open design question: how to handle cluster-scope creds (separate `cluster_credentials` table vs. replicate-on-rows vs. hybrid). Surfaced during 38.1 discuss-phase as the eventual end state; deferred because it would balloon Phase 38.1 scope and the cluster-scope wart needs proper design time. Phase 39 unblock takes priority. **→ v1.8 backlog.**
- **Phase 39 AST-guard scope extension** — when Phase 39 adds unknown/changed-detection helpers (likely as functions called from `scan_infrastructure_drift`), extend D-15's target list to cover them. Not a deferral — just a known future-edit point.
