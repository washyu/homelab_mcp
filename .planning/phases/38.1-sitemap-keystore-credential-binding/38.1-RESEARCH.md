# Phase 38.1: Sitemap-keystore credential binding — Research

**Researched:** 2026-04-26
**Domain:** Credential resolution / database schema / drift-loop refactor (Python 3.12, SQLite + Postgres)
**Confidence:** HIGH (all touch points verified in source; all decisions locked by SPEC + CONTEXT)
**Researcher:** gsd-researcher
**Inputs:** 38.1-SPEC.md (10 reqs locked), 38.1-CONTEXT.md (D-01..D-26 locked), live source inspection of every referenced touch point

## Summary

This phase inserts an opaque `credential_id` UUID join layer between the credential registry (`~/.homelab_mcp/credential_registry.json`) and the sitemap `devices` table so that drift detection can reach Proxmox/SSH hosts whose sitemap-stored hostname spelling differs from the registry-stored hostname spelling. The work spans **8 source files** plus a new AST regression test class — most edits are surgical (add one keyword-only param, add one column, add one bucket, add one CLI subparser pair) and follow existing analogs from Phases 35/36/37/38.

There are **no new external dependencies**: stdlib `uuid` covers UUIDv4 generation; existing `migration.py` patterns extend cleanly; the AST regression scaffolding from Phase 35 D-15 is a near-verbatim template for D-15's "no `Continue` in scan_drift's row loop" guard.

The single non-trivial planning decision left to the planner is the **exception→reason mapping wiring** in the drift loop (D-08 enum codes vs. CONTEXT D-12's "differentiate via context, not subclass") — concretely: should drift call resolver code that returns a sentinel tuple, or should it inspect `CredentialNotFoundError.args[0]` substrings, or should a small helper translate `(exception, did_we_pass_credential_id, did_registry_lookup_hit)` → `reason` enum? See Open Questions §1.

**Primary recommendation:** Plan the work as **6 waves** matching the data-flow order: (Wave 0) AST + functional test scaffolds, (1) `credential_store.py` UUID + registry schema, (2) `database.py` adapter columns + `migration.py` destructive migration with version stamp, (3) resolvers `credential_id=` keyword-only param, (4) `drift_detection.py` loop refactor + `not_eligible` bucket, (5) `server.py` CLI auto-bind side-effects + `link/unlink` + `remove` cleanup + `list --json`, (6) `sitemap.py` / `network_handlers.py` `eligibility` field + `discover_and_map` auto-bind. Each wave can be plan-checked + verified independently; only Wave 6 has a hard cross-wave dependency (it needs Waves 1-3 done because it threads the `credential_id` from resolver → upsert).

## User Constraints (from CONTEXT.md)

### Locked Decisions (D-01 through D-26)

**Auto-bind ambiguity policy (D-01..D-07):**
- **D-01** Canonical workflow is `credentials add` → `discover_and_map` → `scan_infrastructure_drift`. No matching sitemap row at `add` time is the EXPECTED state — silent (no error, no warning, just the existing `Stored ... credential for ...` line).
- **D-02** Keep `hostname` as the registry's natural-key field. SSH+Proxmox overlap on the same host is handled by separate `credential_type` keying and the two-column binding. Friendly-name rename deferred to v1.8.
- **D-03** Credential `hostname` field stays an opaque label — accept any string (IP, short name, FQDN). Auto-bind matches on `hostname == registered_hostname OR connection_ip == registered_hostname`. Multi-match is rare.
- **D-04** Single-match WITH existing non-null binding (overwrite case): interactive prompt using hostname only, no UUIDs in user-facing text. Prompt: `Sitemap row "<hostname>" is already bound to a different <type> credential. Overwrite the mapping? [y/N]:`. Credential is still stored regardless of the answer.
- **D-05** Non-TTY behavior on overwrite/multi-match prompt: skip the bind, print warning, exit 0. Default-safe; no surprise rebinds in unattended scripts. Credential is still stored.
- **D-06** Multi-match (>1 sitemap row matches): interactive prompt with numbered hostname choices. Hostnames only. Non-TTY → skip + warn.
- **D-07** Cluster-scope `credentials add --scope cluster:<name>` skips auto-bind entirely. `proxmox_credential_id` stays NULL on cluster-served rows; drift's resolver Tier-2 cluster walk still resolves them at scan time.

**`not_eligible` shape + sitemap eligibility field (D-08..D-10):**
- **D-08** `not_eligible[].reason` is a small enum + companion `message` field for the human sentence. Enum values: `unbound`, `keyring_desync`, `binding_stale`, `degenerate`. Shape: `{reason: "unbound", message: "No proxmox credential bound; run \`credentials add --type proxmox <hostname>\` to bind."}`.
- **D-09** Cluster-served rows: drift's loop reads the binding; if NULL it still calls `resolve_proxmox_credentials(hostname)` which does the Tier-2 cluster walk. Success → `probed_ok` / `unreachable` normally (NOT `not_eligible`). Hard failure → `not_eligible` with `reason="unbound"`. SPEC acceptance criterion for `counts.not_eligible` is refined: equals `COUNT(*) WHERE proxmox_credential_id IS NULL AND no cluster credential resolves the row` (after filter). `eligibility.proxmox` on `get_network_sitemap` still reflects binding-state only (false for cluster-served rows).
- **D-10** `eligibility` field shape on `get_network_sitemap` rows is the SPEC-literal bool pair: `{ssh: bool, proxmox: bool}`. `true` when `<type>_credential_id IS NOT NULL`, `false` otherwise. Pure binding-state — no resolver runs at sitemap-read time.

**Resolver `credential_id` mismatch behavior (D-11..D-14):**
- **D-11** Stale binding: `resolve_*_credentials(host, credential_id=<uuid>)` when UUID is NOT in the registry → raises `CredentialNotFoundError` with `binding stale: UUID <x> not in registry`. **Never falls back** to hostname-exact-match. Drift catches the exception and routes the row to `not_eligible` with `reason="binding_stale"`.
- **D-12** Keyring desync: UUID hits a registry entry but the keyring secret returns None → raises `CredentialNotFoundError` with the desync warning shape (mirrors `proxmox_api.py:228-236`). Drift maps to `not_eligible` with `reason="keyring_desync"`. Same exception class as D-11; differentiation via context, not subclass.
- **D-13** When both `credential_id=<uuid>` AND `host` are passed, and the UUID's entry has a `hostname` field that doesn't match `host`: **UUID wins, host is ignored** for lookup purposes. The mismatch is the EXPECTED case, not an error.
- **D-14** Both resolvers gain `credential_id` as a **keyword-only parameter, default `None`**. Existing positional callers keep working unchanged.

**AST guard pattern for "no silent skip" (D-15..D-18):**
- **D-15** Forbid every `ast.Continue` inside the row-loop body of `drift_detection.scan_drift` (NOTE: the function name is `scan_drift`, not `scan_infrastructure_drift` — the latter is the MCP tool name; see Pitfall 1 below).
- **D-16** Guard scope is **only `scan_drift` for now** (matches Phase 35 D-15's targeted scope).
- **D-17** Existing degenerate-row filter at `drift_detection.py:142-143` is **converted to bucket routing** — degenerate rows land in `not_eligible` with `reason="degenerate"`. No allowlist, no AST exemption.
- **D-18** Add a **functional regression test alongside the AST guard**. Fixture: 1 NULL-binding row + 1 bound row + (optional) 1 degenerate row. Run `scan_drift`. Assert routing.

**Migration banner + ordering (D-19..D-22):**
- **D-19** Migration is **startup-fired with a version-stamp guard** (`~/.homelab_mcp/migration_state.json` recording `phase_38_1_applied: true` + timestamp). Idempotent.
- **D-20** Order: (1) backup registry → (2) drop devices table → (3) stamp version. If step 2 fails, the stamp isn't written; re-run picks up where it left off.
- **D-21** User-visible banner is **multi-line stderr output with recovery steps inline**, mirroring the v1.6 `ssh_credentials` drop banner at `migration.py:54-62`. Three blocks: what / why / recovery commands.
- **D-22** When `.bak.<timestamp>` already exists, **always use a fresh timestamp; never overwrite**. Idempotency comes from the version stamp (D-19), not from the bak filename.

**`link/unlink` CLI shape + UUID surfacing (D-23..D-26):**
- **D-23** UUIDs surface in **`credentials list --json` only**. Default tabular `credentials list` stays UUID-free.
- **D-24** `credentials link` accepts **UUID only** — single-shape API: `credentials link <sitemap_hostname> <credential_id> --type {ssh,proxmox}`. No auto-detect, no hostname-tuple alias.
- **D-25** `credentials link` validates that the supplied `credential_id` belongs to an entry whose `credential_type` matches `--type`. Mismatched type → actionable error.
- **D-26** When `credentials remove <hostname>` nulls sitemap bindings, the CLI prints affected rows on stderr, hostnames only: `Unlinked sitemap row(s): <hostname1>, <hostname2>`. Zero-bound: print quiet `No sitemap bindings to clean up.` or nothing.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| UUID generation | Credential layer (`credential_store.py`) | — | Registry owns its identity space; CRED-04 no-import constraint means it cannot read DB; UUID generation is local concern |
| Schema migration | Database layer (`database.py` + `migration.py`) | — | Migration is per-adapter; `init_schema` calls `run_*_migrations` already |
| Auto-bind side-effect at `add` | CLI layer (`server.py`) | DB layer | CLI handler runs registration, then queries DB; DB exposes a method to read+write the binding column; CLI orchestrates |
| Auto-bind side-effect at discovery | Sitemap layer (`sitemap.py` upsert path) | Resolver layer (`ssh_tools.py`) | Resolver returns the entry it used; sitemap upsert reads its UUID and writes the binding column |
| Resolver UUID short-circuit | Resolver layer (`proxmox_api.py`, `ssh_tools.py`) | — | Resolver owns identity → secret mapping; UUID lookup is a new path through the registry |
| Drift bucket routing | Drift loop (`drift_detection.py`) | Resolver layer (raises) | Drift owns the four-bucket envelope; resolver raises typed exceptions; drift translates exception → bucket+reason |
| Eligibility surfacing | Sitemap row serializer (DB adapter `get_all_devices` flatten) + Drift envelope | — | `eligibility` is pure DB-row state; `not_eligible` is drift-loop state |
| Migration version stamp | Migration layer (`migration.py`) | — | First version-stamp pattern in codebase; lives next to existing migration code; uses `~/.homelab_mcp/` dir already owned by `credential_store.py` |

### Pattern 1: Keyword-only resolver param (D-14)
**What:** Add `credential_id: str | None = None` as keyword-only after `*` in both resolver signatures.
**When to use:** Universally — every signature change for a new optional resolver knob in this codebase uses this pattern (Phase 34 added `session=` the same way).
**Example (verified — `proxmox_api.py:196`):**
```python
async def resolve_proxmox_credentials(
    host: str,
    *,
    session: aiohttp.ClientSession | None = None,
    credential_id: str | None = None,  # NEW (D-14)
) -> tuple[str, Literal["node", "cluster"], str | None]:
    ...
    if credential_id is not None:
        # D-13: UUID wins — host is ignored for lookup; used only for log/error context
        entry = _find_entry_by_credential_id(credential_id)  # new helper in credential_store
        if entry is None:
            # D-11: never fall back to hostname-exact-match
            raise CredentialNotFoundError(
                f"binding stale: UUID {credential_id} not in registry. "
                f"Run `homelab-mcp credentials add --type proxmox {host} <username>` "
                "to register, or `credentials unlink ... --type proxmox` to clear the binding."
            )
        secret = get_credential(entry["hostname"], entry["username"], credential_type="proxmox", ...)
        if secret is None:
            # D-12: keyring desync (registry hit, keyring miss)
            raise CredentialNotFoundError(f"keyring desync for credential_id={credential_id}: ...")
        return (f"{entry['username']}={secret}", entry.get("scope", "node"), entry.get("cluster_name") or None)
    # ... existing tier-1 + tier-2 logic ...
```

### Pattern 2: Idempotent ALTER TABLE ADD COLUMN (R2)
**What:** Use `PRAGMA table_info(devices)` set-difference shape that Phase 35/38 already use.
**When to use:** Adding a column to `devices` on an existing schema. Re-runs are no-ops.
**Example (verified — `migration.py:69-79`):**
```python
# Phase 38.1 R2: ADD COLUMN for ssh_credential_id + proxmox_credential_id
cursor.execute("PRAGMA table_info(devices)")
existing_columns = {row[1] for row in cursor.fetchall()}
newly_added: list[str] = []
for new_col in ("ssh_credential_id", "proxmox_credential_id"):
    if new_col not in existing_columns:
        cursor.execute(f"ALTER TABLE devices ADD COLUMN {new_col} TEXT")  # noqa: S608
        newly_added.append(new_col)
if newly_added:
    conn.commit()
    for col in newly_added:
        applied_migrations.append(f"add_column_{col}")
```

**Postgres analog:** `ALTER TABLE devices ADD COLUMN IF NOT EXISTS <col> TEXT` (Postgres supports `IF NOT EXISTS` directly; SQLite does not). Use `TEXT` on both adapters for parity per SPEC R2 ("SQLite `TEXT`, Postgres `UUID` or `TEXT` for parity") — pick `TEXT` for both so the format is identical and the resolver doesn't need adapter-aware UUID parsing.

### Pattern 3: Schema-rebuild dynamic-column copy (when devices table needs full recreate)
**What:** Phase 35's `devices_new` table-rebuild pattern (`migration.py:160-235`).

### Anti-Patterns to Avoid

- **AST guard scope creep:** Do not extend D-15's guard to other drift helpers in this phase. CONTEXT D-16 explicitly scopes it to `scan_drift` only; Phase 39 will extend.
- **Subclassing `CredentialNotFoundError`:** D-12 locks single-class differentiation via context. Adding subclasses creates a class-hierarchy that drift would have to except-on, which forces resolver and drift to keep their exception taxonomies in lockstep — fragile.
- **Adapter divergence on column type:** Use `TEXT` on both SQLite and Postgres for the binding columns. Postgres `UUID` type rejects null/empty-string with adapter-specific errors; `TEXT` is uniformly nullable and adapter parity matters per SPEC §Constraints (Pitfall 4).
- **Ambiguous prompt-default semantics:** D-04 says `[y/N]` — capital N means default-no on bare Enter. The `input()` reader must treat `""` as "N", not as "ambiguous re-prompt". Match the existing `_cmd_credentials_*` style of treating empty input as a default selection.
- **Calling resolver with `credential_id=None` to mean "no binding":** Pass `credential_id` only when the row has a non-null binding. Passing `credential_id=None` should fall through to the existing tier-1/tier-2 path (D-09 cluster-served rows depend on this).

## Common Pitfalls

### Pitfall 1: Function name confusion — `scan_drift` vs `scan_infrastructure_drift`
**What goes wrong:** AST guard targets `scan_infrastructure_drift` (the SPEC-quoted name) and silently passes because that function doesn't exist in `drift_detection.py`.
**Why it happens:** SPEC.md and CONTEXT.md repeatedly say `scan_infrastructure_drift` because that's the MCP tool name. The actual Python function is `scan_drift` (verified at `drift_detection.py:54`). The MCP tool handler at `tool_handlers/drift_handlers.py:9` is `handle_scan_infrastructure_drift` and it calls `scan_drift`.
**How to avoid:** AST guard targets `scan_drift` literally. Tests assert `target is not None` so a typo fails fast.
**Warning signs:** `assert target is not None` passes against an unrelated function (or fails at the assertion itself).

### Pitfall 2: SPEC R7 acceptance equation needs CONTEXT D-09 refinement
**What goes wrong:** Tests write `assert response['counts']['not_eligible'] == count_where_proxmox_credential_id_is_null` and fail on cluster-served rows.
**Why it happens:** SPEC R7 acceptance says `counts.not_eligible == COUNT(*) FROM devices WHERE proxmox_credential_id IS NULL (after filter)` — but D-09 refines this: cluster-served rows have NULL binding AND resolve via Tier-2 cluster walk → they go to `probed_ok` or `unreachable`, NOT `not_eligible`. The correct equation is `COUNT(*) WHERE binding IS NULL AND no cluster credential resolves the row`.
**How to avoid:** D-09 is the binding decision; SPEC's acceptance equation is the unrefined first-pass. Tests assert membership in the right bucket, not the simplified count equation.
**Warning signs:** Test fixture has a cluster-scoped credential + a row with NULL binding that the cluster credential can resolve; assertion fails on bucket count.

### Pitfall 3: Adapter parity slip on column type
**What goes wrong:** SQLite uses `TEXT`; Postgres uses native `UUID`; a stale binding string `"not-a-uuid-at-all"` passes SQLite but Postgres adapter raises a `psycopg2.errors.InvalidTextRepresentation` when reading.
**Why it happens:** Postgres `UUID` type rejects malformed strings on read+write; SQLite `TEXT` accepts anything.
**How to avoid:** Use `TEXT` on both adapters. SPEC says "SQLite `TEXT`, Postgres `UUID` or `TEXT` for parity" — pick `TEXT` for parity. Validate at the resolver layer with a stdlib `uuid.UUID(str_value)` round-trip.
**Warning signs:** `psycopg2.errors.InvalidTextRepresentation` in CI Postgres tests.

### Pitfall 4: `CredentialNotFoundError` differentiation collapses
**What goes wrong:** Drift catches `CredentialNotFoundError` and routes everything to `not_eligible.reason="unbound"` regardless of whether the actual cause was stale-binding (D-11) or keyring-desync (D-12).
**Why it happens:** D-12 locks single-class. The differentiation requires inspecting either (a) exception message substrings or (b) a context flag the resolver sets on the exception.
**How to avoid:** Recommend the helper-function approach: `_classify_resolver_failure(exc, did_pass_credential_id, did_registry_lookup_hit) -> str` where the resolver mutates an attribute on the exception (or returns a 2-tuple `(token, reason_hint)` on miss). See Open Questions §1.
**Warning signs:** Functional test (D-18 fixture) shows `not_eligible[0].reason == "unbound"` when fixture set up a stale-binding scenario.

### Pitfall 5: TTY detection wrong for `add` overwrite prompt (D-04/D-05)
**What goes wrong:** CI runs `credentials add` against a hostname that has a binding, hangs forever waiting for stdin, or skips silently when it should have prompted.
**Why it happens:** D-05 mandates non-TTY → skip + warn (default-safe). The check must use `sys.stdin.isatty()` BEFORE calling `input()`.
**How to avoid:** Branch on `sys.stdin.isatty()`:
- TTY: prompt with `input()`, parse y/N, default-no.
- Non-TTY: skip the bind, print warning to stderr, exit 0 (credential is still stored).
**Warning signs:** CI test for `credentials add` with auto-bind binding-overwrite hangs OR auto-rebinds without warning in non-TTY.

### Pitfall 6: Migration ordering trap if step 2 fails after step 1 succeeds
**What goes wrong:** Backup written, drop fails, version-stamp not written → next startup re-archives (creating a SECOND `.bak.<ts>` file) and re-attempts the drop.
**Why it happens:** D-20 explicitly orders this way: backup first, then drop, then stamp. If drop fails, the user may have to manually intervene. Repeat-archives are intentional per D-22 ("always use a fresh timestamp; never overwrite").
**How to avoid:** Document the recovery sequence in release notes. The repeat-archive behavior is BY DESIGN — disk litter is KB-scale and idempotency comes from the version stamp.
**Warning signs:** None — this is correct-by-design behavior, but it should be called out in plan tasks so the planner doesn't accidentally introduce overwrite logic.

### Pitfall 7: Auto-bind on `credentials add` with cluster-scope (D-07)
**What goes wrong:** `credentials add --scope cluster:<name>` triggers auto-bind to all sitemap rows that match `hostname == cluster_name` (which is rare but possible) — a bug.
**Why it happens:** The auto-bind branch needs a top-of-handler short-circuit on `scope == "cluster"`. D-07 explicitly says skip auto-bind for cluster-scope.
**How to avoid:** First condition in the auto-bind block: `if scope == "cluster": return  # D-07`. Resolver Tier-2 cluster walk handles them at scan time anyway.
**Warning signs:** Functional test for `credentials add --scope cluster:home <username>` shows a sitemap row with `proxmox_credential_id` non-null afterward.

### Pitfall 8: `credential_store.py` import constraint (CRED-04)
**What goes wrong:** Adding a `from .database import ...` to `credential_store.py` to do auto-bind from inside `register_credential` creates a circular import (database imports from credential layer indirectly via tools).
**Why it happens:** CRED-04 architectural rule: `credential_store.py` is import-leaf-only. Auto-bind side-effects MUST live in the CALLER (CLI handler / discovery flow), not inside `register_credential`.
**How to avoid:** `register_credential` returns the new UUID (or stays void and a sibling `get_credential_by_natural_key` helper retrieves it). Auto-bind happens in `_cmd_credentials_add` which CAN import from database. See architectural responsibility map above.
**Warning signs:** Lint catches `from .database` in `credential_store.py`. Tests that import `credential_store` without going through `homelab_mcp.__init__` fail.

### Migration version stamp + destructive sequence (R10, D-19..D-22)
```python

import json  # noqa: PLC0415
from datetime import UTC, datetime  # noqa: PLC0415
```

## Open Questions

1. **Exception-to-reason mapping wiring (Claude's Discretion in CONTEXT D-08/D-12).**
   - What we know: D-08 locks the four reason codes (`unbound`, `keyring_desync`, `binding_stale`, `degenerate`). D-12 locks "single exception class, differentiate via context." Drift catches `CredentialNotFoundError` and needs to know WHY.
   - What's unclear: Three viable wirings: (a) inspect `exc.args[0]` substring (e.g., `"binding stale" in str(exc)` → stale; `"keyring desync"` → desync; else → unbound); (b) attach a `.reason_hint: str` attribute to the exception in the resolver and read it in drift; (c) make the resolver return a sentinel instead of raising for the structured cases (changes the resolver's contract for non-passing-credential_id callers).
   - Recommendation: **Option (b)** — `exc.reason_hint = "binding_stale"` set in the resolver, default `None` for the existing tier-1/tier-2 raise path which means "unbound" in drift. Cheapest to implement, doesn't change exception class hierarchy (D-12 compliant), and keeps resolver return-type stable. Document in the resolver docstring.

2. **`get_all_devices` flatten path for `eligibility` field (R7).**
   - What we know: `get_all_devices` returns dicts keyed by column name. SQLite returns columns directly; Postgres flattens `system_info` JSONB into top-level keys.
   - What's unclear: Should `eligibility` be added inside the adapter's `get_all_devices` (so every consumer gets it) or only in the network-handler that builds the sitemap output?
   - Recommendation: **Add it inside `get_all_devices` of both adapters** so the field is column-derived (`{"ssh": row["ssh_credential_id"] is not None, "proxmox": row["proxmox_credential_id"] is not None}`). Future MCP tools that read `get_all_devices` get it for free.

3. **`DatabaseAdapter` abstract method for credential binding writes.**
   - What we know: `database.py` exposes `update_device_fingerprint` (Phase 38) and `store_device` for two specific column-write paths. No generic "set this column" method exists on the abstract base.
   - What's unclear: Should auto-bind use a generic `execute_query` (only on SQLite per `database.py:449`) or a typed method like `bind_credential(device_id: int, credential_type: str, credential_id: str | None) -> None`?
   - Recommendation: **Add a typed adapter method** `set_device_credential_binding(device_id: int, credential_type: str, credential_id: str | None) -> None` to the abstract base + both adapter implementations. Mirrors `update_device_fingerprint`'s shape; encapsulates `WHERE id = ?` vs `WHERE id = %s` differences; keeps mypy happy.

4. **Schema migration test fixture choice (Claude's Discretion).**
   - What we know: Test conventions in this repo use both `:memory:` SQLite (most unit tests) and `tmp_path`-based file SQLite (some integration tests). Postgres tests use Docker (`tests/integration/`).
   - What's unclear: Which fixture for the destructive R10 migration?
   - Recommendation: **`tmp_path`-based file SQLite** for the SQLite path (so the registry JSON file path can be patched alongside the DB path), and **mark the Postgres equivalent as `@pytest.mark.integration`** so it runs in the Docker integration suite without slowing down the unit suite. Document the directory layout: monkeypatch `_REGISTRY_PATH` and `_MIGRATION_STATE_PATH` to live under `tmp_path`.
