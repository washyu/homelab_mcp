<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Disk → server startup migration | Migration runs on every server start; reads/writes the local SQLite/Postgres database |
| Migration banner → stderr | Banner emits to operator's stderr; potential information surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-02-01 | Tampering / Information Loss | Pre-existing `drift_baselines` rows on user installs | accept | Per DRFT-21 architectural decision; documented in banner. No security impact (rows store config snapshots, not credentials) |
| T-36-02-02 | Information Disclosure | Stderr banner reveals presence of legacy table | accept | Banner is operator-facing only (stderr, not network-exposed); reveals only the architectural decision, not user data. Matches Phase 33 ssh_credentials banner shape |
| T-36-02-03 | Denial of Service | Migration step runs on every startup | mitigate | Idempotent `IF EXISTS` check makes second run a no-op. Constant-time existence check via `sqlite_master`/`information_schema`. No risk of repeated DROPs |
| T-36-02-04 | Tampering | DROP TABLE could be triggered against an unrelated `drift_baselines` table in user's external Postgres | accept | The migration uses the application's own DB connection via `run_postgres_migrations`. If a user has co-located their unrelated table in this app's database, that's their architectural choice. Mirrors Phase 33's identical pattern for ssh_credentials |
</threat_model>
