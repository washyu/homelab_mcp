# Phase 41.1: Test Isolation & Keyring Hygiene — Research

**Researched:** 2026-04-29
**Domain:** pytest fixture architecture, OS keyring stubbing, AST-based regression guards
**Confidence:** HIGH

## Summary

Phase 41.1 closes a real-world test-isolation leak surfaced in the 2026-04-28 UAT
session: integration tests under `tests/integration/test_credential_binding_round_trip.py`
write `fake-secret-token` into the developer's Windows Credential Manager (or macOS
keychain / Linux secret-service) because the keyring monkeypatch in
`_setup_isolated_environment` lives at function scope, not session-autouse scope.
A second leak — `test-host`/`test-user` keyring entries — needs source identification.

The fix has three architecturally distinct pieces: (1) a session-autouse keyring
fixture in **the root `tests/conftest.py`** that swaps the active keyring backend
to an in-memory implementation before any test or fixture imports `keyring`; (2) an
AST regression guard in `tests/test_ast_regression.py` mirroring the existing
`TestPhase39_1NoSkipInDriftEnum` shape, scanning `tests/` for `store_credential` /
`register_credential` calls outside fixtures that monkeypatch both the keyring AND
`_REGISTRY_PATH`; (3) a pre/post snapshot helper that records `~/.homelab_mcp/` and
the keyring state before the fixture activates and asserts they're unchanged at
session teardown.

**Primary recommendation:** Use `keyring.set_keyring(InMemoryBackend())` in a
session-scoped autouse fixture in the root `tests/conftest.py`, AND additionally
`monkeypatch.setattr` the three module-level functions (`keyring.set_password` /
`keyring.get_password` / `keyring.delete_password`) for belt-and-braces coverage.
The dual approach is required because production code does **lazy imports** of
`keyring` inside function bodies — see [credential_store.py:57-71](../src/homelab_mcp/credential_store.py#L57)
— so an unsuspecting test that imports `keyring` *before* the fixture installs
the in-memory backend would otherwise resolve to the OS backend. Belt-and-braces.

### Pattern 1: Session-autouse Keyring Fixture (Dual Defense)

**What:** A session-autouse fixture in `tests/conftest.py` that swaps the active keyring backend AND monkeypatches the module-level functions.

**When to use:** Every test session — the fixture activates with no opt-in required.

**Example sketch:**
```python
# Source: synthesized from existing tests/integration/test_credential_binding_round_trip.py:77-90
#         + keyring 25.6.0 KeyringBackend ABC verified live
import pytest
import keyring
import keyring.backend


class _InMemoryKeyring(keyring.backend.KeyringBackend):
    """Test-only backend. Stores everything in a per-session dict."""
    priority = 1  # type: ignore[misc]  # jaraco.classes property — concrete value required

    def __init__(self) -> None:
        self._store: dict[tuple[str, str], str] = {}

    def set_password(self, service: str, username: str, password: str) -> None:
        self._store[(service, username)] = password

    def get_password(self, service: str, username: str) -> str | None:
        return self._store.get((service, username))

    def delete_password(self, service: str, username: str) -> None:
        self._store.pop((service, username), None)


@pytest.fixture(scope="session", autouse=True)
def _isolate_keyring(tmp_path_factory: pytest.TempPathFactory) -> Iterator[None]:
    """Phase 41.1: prevent any test from writing to the real OS keyring.

    Layer 1 (set_keyring): swaps the active keyring backend. Catches code
        that uses keyring.get_keyring().get_password(...) directly.
    Layer 2 (monkeypatch): overrides keyring.set_password/get_password/
        delete_password. Catches code that does `import keyring` inside a
        function body (production credential_store.py pattern).
    Layer 3 (_REGISTRY_PATH redirect): redirects the JSON registry file
        to a per-session tmp_path so the home directory is untouched.

    Snapshots ~/.homelab_mcp/credential_registry.json + Windows Credential
    Manager / macOS keychain / Linux secret-service entries before yielding,
    re-snapshots at teardown, and asserts no drift.
    """
    # 1. Pre-snapshot
    pre = _capture_real_state()

    # 2. Layer 1: swap backend
    original_backend = keyring.get_keyring()
    in_memory = _InMemoryKeyring()
    keyring.set_keyring(in_memory)

    # 3. Layer 2 + 3: monkeypatch (use a session-scoped MonkeyPatch instance)
    mp = pytest.MonkeyPatch()
    keyring_store: dict[tuple[str, str], str] = {}
    mp.setattr("keyring.set_password",
               lambda s, u, p: keyring_store.__setitem__((s, u), p))
    mp.setattr("keyring.get_password",
               lambda s, u: keyring_store.get((s, u)))
    mp.setattr("keyring.delete_password",
               lambda s, u: keyring_store.pop((s, u), None))

    registry_path = tmp_path_factory.mktemp("homelab_mcp_test") / "credential_registry.json"
    # Both module aliases — see test_credential_binding_round_trip.py:62-65 for prior art
    mp.setattr("homelab_mcp.credential_store._REGISTRY_PATH", registry_path)
    mp.setattr("src.homelab_mcp.credential_store._REGISTRY_PATH", registry_path)

    try:
        yield
    finally:
        mp.undo()
        keyring.set_keyring(original_backend)
        post = _capture_real_state()
        assert pre == post, (
            "Phase 41.1 SC-4: test session leaked state to the developer's "
            f"real OS keyring or ~/.homelab_mcp/. Diff:\n  pre  = {pre!r}\n  post = {post!r}"
        )
```

**Why a session-scoped `pytest.MonkeyPatch()` instance:** the standard `monkeypatch`
fixture is function-scoped, so it cannot be used inside a session fixture. Pytest
exposes `pytest.MonkeyPatch()` as a constructor for exactly this case ([VERIFIED:
pytest 8 docs — `pytest.MonkeyPatch.context()` and direct instantiation are both
supported]).

### Pattern 2: AST Guard for Unprotected Callers

**What:** A new test class in `tests/test_ast_regression.py` that walks every
`tests/**/*.py` file (excluding the conftest itself), finds `Call` nodes whose
`func.id` is `store_credential` or `register_credential`, and asserts the
enclosing scope (function or class) installs both keyring AND `_REGISTRY_PATH`
monkeypatching — OR is on an explicit allowlist.

**When to use:** Permanent regression guard. Same place and shape as the
existing Phase 39.1 R6-regression guard.

**Pattern reference:** `tests/test_ast_regression.py:853-983`
(`TestPhase39_1NoSkipInDriftEnum`) — almost identical AST shape:
1. parse target file with `ast.parse(source, filename=...)`
2. find all `ast.Call` nodes where `n.func.id == "<symbol>"`
3. for each call site, walk parents to determine context
4. emit clear violation messages with line numbers

**Pseudo-shape:**
```python
class TestPhase41_1KeyringHygiene:
    """Phase 41.1 SC-2: every store_credential/register_credential call in
    tests/ must be inside a function/method that monkeypatches both the
    keyring AND _REGISTRY_PATH (OR is in the allowlist for files known to
    rely solely on the session-autouse fixture).
    """

    _GUARDED_SYMBOLS = ("store_credential", "register_credential")
    # Files where the session-autouse fixture is sufficient — explicit
    # allowlist so CI fails LOUDLY on net-new tests that forget protection.
    _ALLOWLIST = frozenset({
        "tests/conftest.py",                         # the fixture itself
        "tests/test_credential_store.py",            # uses mocker.patch keyring + monkeypatch _REGISTRY_PATH per-test (existing pattern)
        # ...explicit per-file approval...
    })

    def test_no_unprotected_credential_writes_in_tests(self) -> None:
        tests_root = Path(__file__).parent
        violations: list[str] = []
        for py_file in sorted(tests_root.rglob("*.py")):
            rel = py_file.relative_to(tests_root.parent).as_posix()
            if rel in self._ALLOWLIST:
                continue
            tree = ast.parse(py_file.read_text(encoding="utf-8"))
            for node in ast.walk(tree):
                if (isinstance(node, ast.Call)
                    and isinstance(node.func, ast.Name)
                    and node.func.id in self._GUARDED_SYMBOLS):
                    violations.append(f"{rel}:{node.lineno} — {node.func.id}(...)"
                                      " not in allowlist; rely on session-autouse"
                                      " fixture or add to _ALLOWLIST with comment")
        assert not violations, "Phase 41.1 SC-2: unprotected callers...\n" + "\n".join(violations)
```

**Why allowlist instead of "verify monkeypatch present":** Detecting whether a
test installs both monkeypatches via AST is brittle (defaults, indirect helpers,
fixture-injected setup). The session-autouse fixture is the load-bearing safety
net; the allowlist documents which test files were audited and confirmed safe.
A new test that writes credentials trips the guard, forcing an explicit decision.

### Anti-Patterns to Avoid

- **Anti-pattern: function-scoped fixture or per-test setup.** The leak in
  `test_credential_binding_round_trip.py` exists *despite* per-test
  monkeypatching because that monkeypatch only fires when the helper
  `_setup_isolated_environment` is called from within a test function. If a
  future test forgets to call it (or imports `keyring` at module-import time),
  there's no safety net. Session-autouse is mandatory.

- **Anti-pattern: monkeypatching only `keyring.set_password` etc. without also
  swapping the backend.** Today's production code uses lazy imports inside
  function bodies, so `mp.setattr("keyring.set_password", ...)` works. But the
  `keyring.get_keyring().set_password(...)` indirect-call form would bypass
  this — and any future refactor toward that form would silently re-open the
  leak. Use both layers.

- **Anti-pattern: writing the snapshot assertion as a separate teardown helper
  outside the fixture.** Pytest reorders teardown across fixtures of the same
  scope unpredictably; placing the assertion inside the fixture's `finally`
  block guarantees it runs after the fixture's monkeypatch is reverted but
  before pytest finalizes the session.

- **Anti-pattern: relying on `monkeypatch.setenv("XDG_RUNTIME_DIR", ...)` or
  similar to influence the keyring backend selection.** Backend selection
  varies per OS (Windows uses `WinVaultKeyring`, macOS uses `Keyring`, Linux
  uses `SecretService` or `KWallet`). Backend swap via `set_keyring()` is the
  only OS-agnostic approach.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cross-backend keyring stub | A shim per OS that dispatches to mock files / mock dbus | `keyring.set_keyring(custom_backend)` | The `keyring.backend.KeyringBackend` ABC is precisely this extension point; rolling a per-OS shim re-implements what `set_keyring` already does and risks Windows-specific `pywin32-ctypes` / Linux `secretstorage` import side-effects |
| Walking the registry-JSON file format manually for the snapshot | A custom JSON differ | Hash the file content (sha256) + capture mtime | The registry's exact contents don't matter for the snapshot test — only "did anything change" — so a content hash is sufficient and avoids being tightly coupled to the schema |
| Enumerating "all entries in the OS keyring" cross-platform | Per-backend introspection (Win32 API, dbus calls) | Skip enumeration; assert that `keyring.get_keyring()` is restored AND assert no calls to the real backend by intercepting at fixture-swap boundary | Cross-platform keyring enumeration is messy; the simpler pre/post invariant is "the in-memory backend was active for the whole session, so the real backend was never called" — verifiable by tracking backend identity, no enumeration needed |
| Detecting which test leaked via blame analysis | Custom git instrumentation | Allowlist + AST guard catches new offenders at commit time | The historical leak is fixed once the fixture is in place; the AST guard prevents re-introduction. Forensic tooling is overkill for a homelab single-user repo |

**Key insight:** keyring's `set_keyring()` API exists exactly for testing. Use it.

## Common Pitfalls

### Pitfall 1: `tests/conftest.py` already exists with Phase 39 fixtures

**What goes wrong:** `tests/conftest.py` (existing, confirmed via Read) currently contains only Phase 39 drift-detection fixtures (`freeze_now`, `mock_universal_core_probe_response`, etc.) and has no autouse fixture. Adding a new session-autouse fixture is purely additive — but if the planner naively tells the implementer to "create `tests/conftest.py`," the existing fixtures will be obliterated.
**Why it happens:** Conftest files are easy to overlook because they auto-load.
**How to avoid:** Plan tasks must specify "ADD to existing `tests/conftest.py`" and reference the Phase 39 fixture preservation requirement.
**Warning signs:** Phase 39 drift tests fail after Phase 41.1 lands.

### Pitfall 2: The leaking test's exact source is non-obvious

**What goes wrong:** The phase description identifies `test_credential_binding_round_trip.py` as the keyring leaker, but says "the leaked `test-host`/`test-user` SSH entry source needs identification." Grep across `tests/` shows `test-host`/`test-user` literals appear in 8+ test files (`test_ssh_tools.py`, `test_sitemap.py`, `test_service_installer.py`, `test_ansible.py`, `test_mcp_prompts.py`, `test_database.py`, `test_error_handling.py`, `test_config.py`) — most are *parameter values* passed to mocked functions, not real keyring writes. The actual leak path requires runtime investigation, not static grep.
**Why it happens:** `test_ssh_tools.py:104,340,355,372,398` calls `ssh_discover_system(hostname="test-host", username="test-user", password="...")` which DOES NOT write to keyring (verified by grepping `src/homelab_mcp/ssh_tools.py` for `store_credential` — zero hits). `test_sitemap.py:952` calls `register_credential("test-host", "test-user", credential_type="ssh")` which writes ONLY to the registry JSON (not keyring), and the test monkeypatches `_REGISTRY_PATH` to `tmp_path` (line 947-949). So neither candidate leaks to the keyring directly.
**How to avoid:** The plan should include a Wave-0 forensic task: with the new session-autouse fixture **disabled**, run the full test suite and instrument `keyring.set_password` to log `(service, username, traceback)` to a file. The trace will identify the leak site exactly. Rerun with the fixture enabled to confirm closure. Likely candidates after this investigation: a deeply-mocked path that incidentally calls `_cmd_credentials_add` via `argparse.Namespace` (similar to `test_credential_binding_round_trip.py:518`) but in a non-integration test that ran before the integration suite added monkeypatching.
**Warning signs:** Speculation about which test is the leaker without instrumentation.

### Pitfall 3: Lazy `import keyring` defeats `set_keyring()` if a test imports keyring eagerly

**What goes wrong:** `credential_store.py` does `import keyring` *inside* `store_credential` (line 58). The fixture's `keyring.set_keyring(InMemoryBackend())` swaps the global. But if a test file does `import keyring` at module level AND calls `keyring.set_password(...)` directly (rather than going through `store_credential`), the fixture intercepts via Layer 2 (`monkeypatch.setattr("keyring.set_password", ...)`). Verified: existing tests don't call `keyring.set_password` directly except in `test_credential_store.py` (which uses `mocker.patch` per-test, an additional layer).
**Why it happens:** Two valid keyring API surfaces (`keyring.set_password(...)` shorthand vs `keyring.get_keyring().set_password(...)`); fixture must cover both.
**How to avoid:** Both layers in the fixture (set_keyring + monkeypatch.setattr).
**Warning signs:** Snapshot assertion fails despite fixture being installed.

### Pitfall 4: pytest collection order and module-import-time keyring access

**What goes wrong:** If any test module does `from keyring import set_password` at the top of the file (eager binding), the session fixture has no chance to intercept — by the time the fixture runs, the local name `set_password` already points at the real function.
**Why it happens:** Python's import semantics — `from X import Y` binds `Y` to the name at import time, not lookup time.
**How to avoid:** Add an AST guard to `test_ast_regression.py` checking that no test file does `from keyring import (set|get|delete)_password`. Verified via grep: no current test does this. Lock it in.
**Warning signs:** A specific test passes in isolation but fails in suite (or vice versa).

### Pitfall 5: Windows Credential Manager doesn't expose enumeration via the standard `keyring` API

**What goes wrong:** The "pre/post snapshot" success criterion implies enumerating all keyring entries. The `keyring` library does NOT expose a generic `list_all_entries()` — it only has `get_password(service, username)` (lookup) and `set/delete`. Windows backends offer no general enumeration; macOS/Linux have backend-specific options.
**Why it happens:** Cross-platform keyring abstraction is intentionally minimal.
**How to avoid:** Reframe the snapshot from "enumerate all keyring entries" to "verify the in-memory backend was active for the entire session, AND verify the registry JSON file content is bytewise identical pre/post." If the in-memory backend was active throughout, the real backend was never called — that's a stronger invariant than enumeration. Use `keyring.get_keyring()` identity comparison.
**Warning signs:** Plan tasks include "list all entries in Windows Credential Manager."

## Code Examples

### Existing pattern: per-test keyring monkeypatch (test_credential_binding_round_trip.py)

```python
# Source: tests/integration/test_credential_binding_round_trip.py:77-90 (verbatim)
keyring_store: dict[str, str] = {}

def _set_password(svc: str, user: str, pw: str) -> None:
    keyring_store[f"{svc}:{user}"] = pw

def _get_password(svc: str, user: str) -> str | None:
    return keyring_store.get(f"{svc}:{user}")

def _delete_password(svc: str, user: str) -> None:
    keyring_store.pop(f"{svc}:{user}", None)

monkeypatch.setattr("keyring.set_password", _set_password)
monkeypatch.setattr("keyring.get_password", _get_password)
monkeypatch.setattr("keyring.delete_password", _delete_password)
```

This is the closest existing pattern to what Phase 41.1 needs. Phase 41.1 generalizes it to session scope and adds Layer 1 (`set_keyring`).

### Existing pattern: per-test `_REGISTRY_PATH` redirect (test_credential_store.py:130-135)


2. **Should the snapshot assertion fail the session, or warn?**
   - What we know: SC-4 says "verified via fixture pre/post snapshot" — strict reading is "test fails on drift"
   - What's unclear: If a CI quirk causes spurious drift (e.g., timezone in mtime), should this hard-fail or log
   - Recommendation: Use sha256 of file content (no mtime), and HARD-fail. If the assertion ever trips, that's a real leak — diagnose, don't suppress.

   - What we know: `find_credential_by_id` is read-only and doesn't write
   - What's unclear: Whether the guard's symbol set should be tightened to write-only functions
   - Recommendation: Guard only `store_credential` (writes keyring) and `register_credential` (writes registry JSON). Lookup helpers don't leak.
