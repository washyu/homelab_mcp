Extend `resolve_ssh_credentials()` in `src/homelab_mcp/ssh_tools.py` so a caller that provides only `hostname` (with `username=None`) resolves the username from the keyring registry — in BOTH tiers. Remove the silent `or "mcp_admin"` fallback on line 63. Implements D-04 and D-04a from `33.1-CONTEXT.md`.

Purpose: Phase 33 landed keyring-only two-tier resolution, but the resolver still requires the caller to pass `username` — and the Tier-1 explicit-args branch has a runtime fallback `username or "mcp_admin"` on line 63 that violates D-04's keyring-only contract. Phase 33.1 makes `username` optional at BOTH tier boundaries: the Tier-2 keyring branch gets registry-scan-by-hostname; the Tier-1 branch ALSO does registry-scan-by-hostname when `username` is None (so callers passing `password=` without `username=` get a registry-resolved username instead of the literal "mcp_admin"). Closes the "mcp_admin default everywhere" gap surfaced by live testing 2026-04-21.

Output: Modified `resolve_ssh_credentials()` covering four scenarios:
1. Tier-2 (keyring-only) with `username=None`, single match → success
2. Tier-2 with `username=None`, multi match → actionable ambiguous error
3. Tier-2 with `username=None`, zero match → unchanged CredentialNotFoundError
4. Tier-1 (explicit password/key_path) with `username=None` → same registry-scan-by-hostname logic as Tier-2 (single/multi/zero branching)

Plus positive tests for each branch.

    Suggested helper (module-level private):
    ```python
    def _resolve_username_from_registry(hostname: str) -> tuple[str, list[dict[str, str]]]:
        """Scan the keyring registry for the given hostname; return (resolved_username, matched_entries).

        Raises CredentialNotFoundError for zero-match or multi-match.
        """
        registry_entries = list_credentials(credential_type="ssh")
        matched = [e for e in registry_entries if e["hostname"] == hostname]
        if len(matched) == 0:
            raise CredentialNotFoundError(
                f"No credentials found for {hostname}. "
                f"Run `homelab-mcp credentials add {hostname} <username>` in your terminal."
            )
        if len(matched) >= 2:
            raise CredentialNotFoundError(
                f"Multiple credentials registered for {hostname}: "
                f"{', '.join(sorted(e['username'] for e in matched))}. "
                f"Specify username explicitly, or call list_keyring_credentials "
                f"to inspect registered entries."
            )
        return matched[0]["username"], matched
    ```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP tool input → resolve_ssh_credentials | Untrusted `hostname` string reaches registry enumeration; multi-user match produces error message listing registered usernames |
| credential_store.list_credentials → resolver | JSON hostname registry contents are effectively trusted (server-local file) but their contents surface into error messages |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-33.1-01 | Information Disclosure | `resolve_ssh_credentials` ambiguous-match error message | accept | The error message names registered usernames. This is intentional (D-04a "agent can make a call to list keyring and get the username itself"). Registry contents are already exposed via `list_registered_servers` / `list_keyring_credentials` MCP tools — the resolver error re-surfaces the same information at the same trust level. No PII beyond hostnames and SSH usernames. |
| T-33.1-02 | Tampering | Registry file on disk | accept | Server trusts its own on-disk JSON registry (single-user homelab deployment model, Phase 33 D-06 scope). Threat rejected from scope per Phase 33. |
| T-33.1-03 | Denial of Service | Large registry → slow resolver | accept | `list_credentials()` returns a list; multi-user enumeration is O(n) in registered hosts. Homelab scope (tens of hosts max), not a DoS vector. |
| T-33.1-04 | Elevation of Privilege | Caller bypasses username with None to get a different user's credential | mitigate | Single-match branch: server picks the sole registered user for the hostname — that IS the user the caller implicitly authorized (they registered it). Multi-match branch: hard error, server never auto-picks. Zero-match branch: unchanged CredentialNotFoundError. No silent fallback to a different user. BLOCKER 1 fix: the Tier-1 branch's `or "mcp_admin"` fallback is removed — a caller passing `password=` without `username=` no longer silently authenticates as `mcp_admin`; instead the registry is scanned and an error is raised if the registry doesn't resolve unambiguously. |

Residual risk: **low**. The disposition matches Phase 33's D-06 threat model for the keyring registry surface.
