## Bulk Target Schema — `password` Field (D-06 enforcement)

| Option | Description | Selected |
|--------|-------------|----------|
| Remove it | Delete `password` from bulk_discover_and_map AND discover_and_map schemas. Keyring is the only password source. Clean D-06 enforcement. Callers who passed passwords get a schema validation error pointing to `credentials add`. | ✓ |
| Remove bulk only | Drop from `bulk_discover_and_map` (multi-target, higher risk), keep in `discover_and_map` (single-host, already rare). Softer break. | |
| Keep, reject at handler | Leave schema fields, add handler-side validation that raises an actionable error if `password=` is present. Lossier — the schema still documents a field that doesn't work. | |

**User's choice:** Remove it (Recommended)
**Notes:** Straightforward D-06 extension — keyring is source of truth; no password should ever flow through the MCP schema surface.

## Username Default Behavior When Schemas Drop `mcp_admin`

| Option | Description | Selected |
|--------|-------------|----------|
| Resolver looks it up | `resolve_ssh_credentials(hostname, username=None)` scans the registry for entries matching hostname. Single match → use it. Multiple matches → disambiguation error. Zero matches → CredentialNotFoundError pointing to `credentials add`. | ✓ |
| Make username required | Schemas mark `username` as required (parity with D-23 `register_server`). Every call is explicit. Zero ambiguity but every call gets longer. | |
| Error immediately if omitted | Keep username optional in schema but handler raises `ValueError` if None. Self-documenting failure, no registry scan complexity. | |

**User's choice:** (determined from freeform clarification) — Resolver looks it up, with agent self-disambiguation via `list_keyring_credentials` when multiple matches exist.
**Notes:** User explained the model verbatim: "the keyring entry is hostname and username then uses password entry for the password in the CLI so we inject the username and password from the keyring entry. Also I think the agent can make a call to list keyrights and get the username it self if needed." This is captured as D-04 and D-04a in CONTEXT.md.

## `update_mcp_admin_groups` Schema `password` Field

| Option | Description | Selected |
|--------|-------------|----------|
| In scope — drop password field | Remove `password` from `update_mcp_admin_groups` schema. Handler already routes through the resolver, so keyring auto-inject continues to work. | |
| In scope — keep as schema-level escape hatch | Keep `password` field in schema for the rare case where the target user isn't in keyring yet. Deviates from D-06 but preserves a manual path. | |
| Out of scope | Keep Phase 33.1 narrow to sitemap + bulk schemas. Defer to a backlog item. | |
| **Other (freeform):** drop the whole tool | User response extended the scope: drop `update_mcp_admin_groups` entirely, because Phase 33 D-18 made `mcp_admin` non-privileged — a tool that operates on a specific account no longer has a reason to exist. | ✓ |

**User's choice:** Other (freeform) — drop the whole tool.
**User's notes, verbatim:** "we should drop this as we are also removeing the neef for the mcp_admin since again username comes from the keyright so a user dosen't need to create or use the mcp_admin"
**Follow-up:** Scope expansion triggered a disambiguation question about the sibling `verify_mcp_admin_access` tool.

## Sibling Tool — `verify_mcp_admin_access` (follow-up)

| Option | Description | Selected |
|--------|-------------|----------|
| Drop both | Remove `verify_mcp_admin_access` AND `update_mcp_admin_groups` from the MCP tool surface in lock-step: schemas, handlers, dispatch, annotations, openapi, and the underlying ssh_tools.py functions + helpers. Generic equivalents (`ssh_execute_command`) cover the functionality. | ✓ |
| Drop update, keep verify | Remove `update_mcp_admin_groups` but keep `verify_mcp_admin_access` — it's read-only sudo-access check, still useful post-onboarding. | |
| Drop update only, defer verify | Narrow 33.1 to just `update_mcp_admin_groups`. `verify_mcp_admin_access` fate decided later. | |

**User's choice:** Drop both (Recommended)
**Notes:** Symmetric cleanup — both tools are named after a non-privileged account and operate only on it. `ssh_execute_command(hostname, command="sudo -n true")` covers the generic sudo-access check.

## Regression Guards — AST Meta-Test Extensions

| Option | Description | Selected |
|--------|-------------|----------|
| Forbid mcp_admin defaults in function signatures | Extend AST scan to fail if any non-test .py file has `username="mcp_admin"` or `username: str = "mcp_admin"` as a parameter default. Revert-proof for the sitemap.py fix. | ✓ |
| Forbid mcp_admin in MCP schema defaults | Import each TOOLS dict, assert no schema anywhere has `"default": "mcp_admin"` (walks nested item schemas too, catches bulk target). Revert-proof for the schema fix. | ✓ |
| Forbid password in MCP schema properties | Assert no tool schema has a `password` property at any nesting depth. Permanent protocol-boundary enforcement of D-06. | ✓ |
| Skip meta-guards | Rely on positive pytest coverage of the new behavior. Lighter but a future regression isn't caught by a meta-guard. | |

**User's choice:** All three (multiSelect) — skip meta-guards NOT selected.
**Notes:** Full defense-in-depth. Captured as D-08, D-09, D-10 in CONTEXT.md. D-10 in CONTEXT.md also extends the Phase 33 D-15/D-25 forbidden-strings list with the removed tool names.
